# Крипто-анализ загрузчика RP2350 enc_bootloader. Атака по питанию (CPA) и стойкость ключа AES-256

## Апстрим прямо признаёт эту уязвимость

Side-channel здесь — не гипотеза, а заявленное свойство сборки. README апстрима варианта на MbedTLS (именно он прошит на устройстве) пишет дословно:

> This bootloader uses MbedTLS for decryption, so it is not secure against side channel attacks and therefore only offers limited protection against physical attackers

Апстрим даёт и защищённую альтернативу — ассемблерный AES с контрмерами против сторонних каналов, но на устройстве прошит именно **незащищённый** табличный mbedtls (подтверждено таблицами S-box и T-table в дампе и дизассемблером). Значит признанное вендором ограничение применимо напрямую

## Устройство и схема шифрования

Чип RP2350 (Cortex-M33), прошивка — защищённый загрузчик `enc_bootloader` на базе mbedtls. Он читает ключ из одноразовой памяти OTP, расшифровывает образ приложения и передаёт ему управление. Схема (сверено дизассемблером):

- AES-256-CTR: `keystream[k] = AES256-ECB-ENC(key, nonce_k)`, `plaintext = ciphertext XOR keystream`
- инкремент нестандартный: `nonce_k = iv0`, затем `nonce[12..15] ^= big-endian(k)` (XOR, не сложение; старшие 12 байт неизменны)
- `iv0 = IV_public XOR IV_salt`; публичный IV лежит в образе по смещению `0x80014`, соль — в OTP
- ключ AES-256 — 4-way XOR-share в OTP (залочен на чтение), соль — отдельная страница OTP (залочена)

Ключ и соль недоступны штатно: OTP-страницы закрыты на чтение, отладочный порт отключён, а stepping чипа A4 закрыл известные глитч-атаки на кремниевом уровне. Код загрузчика побайтно совпадает с апстримом — модификаций и бэкдора нет. Поэтому единственный остаточный крипто-путь к ключу — физический сторонний канал

## Атака: корреляционный анализ питания (CPA)

Табличный AES при вычислении обращается к таблицам раунда по адресам, зависящим от данных, а энергопотребление чипа зависит от веса Хэмминга обрабатываемых байт. Снимая энергопотребление во время расшифровки (при каждой загрузке), по корреляции с моделью потребления восстанавливают ключ по байтам — `16×256` гипотез вместо `2²⁵⁶`. Классификация — CWE-1300 (Improper Protection of Physical Side Channels). Контрмер в сборке нет: `MBEDTLS_AES_ROM_TABLES` без constant-time и без аппаратного ускорителя. Stepping A4 этот путь **не закрывает** — он чинит глитчи, не сторонние каналы

Физически нужен стенд захвата (ChipWhisperer или осциллограф с шунтом в цепь питания ядра либо ЭМ-зонд), триггер на начало расшифровки и тысячи автоматических перезагрузок для накопления статистики. Это — физическая часть, она в данном отчёте не выполнена за отсутствием стенда; ниже — программное обоснование метода

## PoC на синтетических трассах

`src/cpa_poc.py` моделирует энергопотребление табличного AES (вес Хэмминга промежуточных значений плюс гауссов шум) и прогоняет корреляционный анализ. Железа и дампа не требует. Три сценария:

| Сценарий                      | Атакуемое значение                                    | Вариация входа      | Восстановлено   | Вывод                            |
| ----------------------------- | ----------------------------------------------------- | ------------------- | --------------- | -------------------------------- |
| A — классический CPA          | выход S-box 1-го раунда                               | случайный plaintext | 16/16 байт RK0  | пайплайн валиден                 |
| B — 1-й раунд при фикс. входе | выход S-box 1-го раунда                               | только `nonce[15]`  | 1 байт          | путь через 1-й раунд не работает |
| C — последний раунд           | `InvSbox(keystream XOR rk14)` по известному keystream | только `nonce[15]`  | 16/16 байт RK14 | рабочий метод                    |

Почему 1-й раунд проваливается (B): вход AES фиксирован (один IV на загрузку), счётчик блоков мал, реально меняется только младший байт `nonce[15]`, а байты с застывшим входом дают нулевую корреляцию — извлекается лишь один байт

Почему последний раунд работает (C): CPA атакует не вход, а ВЫХОД — известный keystream. Из-за лавинной диффузии AES изменение даже одного `nonce[15]` меняет весь выход, поэтому все 16 байт последнего round-key `rk14` коррелируют и восстанавливаются целиком. PoC даёт 16/16 байт `rk14` при 256 известных выходах и 13/16 при 12 выходах

Дальше `rk13` восстанавливается тем же приёмом на предпоследнем раунде, а пара `rk13 + rk14` (8 слов) однозначно инвертирует развёртку ключа AES-256 до мастер-ключа. Основной метод — last-round CPA по известному keystream (O'Flynn, IACR eprint 2014/899)

> [!NOTE]
> Как цель рассматривалась и развёртка ключа (`setkey_enc`), но при фиксированном ключе она детерминирована — нулевая дисперсия между трассами, а значит это не CPA, а SPA или template с профилирующим клоном. Годится лишь запасным вариантом при числе известных блоков keystream меньше ~6

## Известный открытый текст

Для last-round CPA нужны известные выходы (keystream-блоки). Первые 16 байт открытого образа известны точно: это векторная таблица приложения (`SP=0x20082000`, `reset=0x20000197`, `NMI=0x2000011b`, `HardFault=0x2000011d`), снятая с отладочного UART живого устройства — Debug-сборка печатает начало расшифрованного образа при загрузке. Этого достаточно для верификации, а предсказуемость векторной таблицы даёт ~12 известных блоков keystream (`keystream_k = CT_k XOR предсказанный PT_k`)

## Оракул верификации ключа

Кандидат ключа, восстановленный физической атакой, проверяется офлайн за один AES — по данным дампа и известному keystream, без доступа к OTP. Соль при этом берётся бесплатно:

```text
keystream[0] = AES256_ECB_ENC(key, iv0),  iv0 = IV_public XOR IV_salt
IV_public = 921e94597201e138c2747ca1e1bd1b0b   (из образа по 0x80014)
цель       = 4a5e4990642bb18272952f73b9854d09   (= CT[0:16] XOR PT[0:16])
iv0  = AES256_ECB_DEC(key, цель)   ->   salt = iv0 XOR IV_public
```

Дальше образ расшифровывается офлайн: `src/decrypt_rp2350.py`, функция `decrypt_with_raw_key`

## Проверки стойкости ключа (отрицательные)

Все дешёвые офлайн-пути к ключу и к зашифрованному блоку `0x300000` закрыты проверенными отрицательными результатами. Оракул перебора точный — сверка `keystream[0]` с `4a5e4990642bb18272952f73b9854d09`:

| Проверка                                                          | Объём                                                           | Результат               |
| ----------------------------------------------------------------- | --------------------------------------------------------------- | ----------------------- |
| Простой/человеческий ключ (`brute_weak_key.py`)                   | 23934 кандидата: строки, составные, паттерны, chip-id × 6 солей | ключ не угадан          |
| Ключ как KDF от chip serial (`brute_serial.py`)                   | 16 функций от серийного номера                                  | мимо                    |
| PIN как ключ блока `0x300000` (`pin_vs_storage.py`)               | 240000 комбинаций: 10⁴ PIN × 6 KDF × 2 CTR × 2 IV, оракул FAT12 | 0 структурных попаданий |
| Самодельная XOR-гамма на `0x300000` (`lastyear_gamma_vs_blob.py`) | 300000 стартовых LBA, оракул FAT12 + энтропия                   | не этот шифр            |

Вывод: ключ — настоящий случайный OTP-секрет, не выводится из публичных данных и не угадывается. Блок `0x300000` зашифрован сильным ключом либо является наживкой, офлайн дешёвыми методами не вскрывается. PIN не входит в ключ — он лишь логический гейт доступа

## Программы

| Файл                            | Назначение                                                                        |
| ------------------------------- | --------------------------------------------------------------------------------- |
| `src/cpa_poc.py`                | CPA на синтетических трассах, сценарии A, B, C (first/last round), самодостаточен |
| `src/brute_weak_key.py`         | перебор простого/человеческого ключа через точный оракул                          |
| `src/brute_serial.py`           | ключ как KDF от серийного номера чипа                                             |
| `src/pin_vs_storage.py`         | гипотеза "PIN = ключ хранилища" против блока `0x300000`                           |
| `src/lastyear_gamma_vs_blob.py` | самодельная XOR-гамма против блока `0x300000` и хвоста                            |
| `src/decrypt_rp2350.py`         | автономный AES-256-CTR дешифратор и оракул, зависимость проверок                  |
| `out/cpa_poc.out`               | сохранённый вывод CPA-PoC                                                         |
| `firmware_dump.bin`             | бинарный дамп прошивки (вход для проверок стойкости)                              |

## Повторение

Из распакованной папки архива:

```bash
python3 src/cpa_poc.py                 # CPA PoC (синтетика, без железа и дампа)
python3 src/brute_weak_key.py          # перебор простого ключа
python3 src/brute_serial.py            # KDF от серийного номера
python3 src/pin_vs_storage.py          # PIN против 0x300000
python3 src/lastyear_gamma_vs_blob.py  # самодельная гамма против 0x300000
```

Проверки стойкости читают `firmware_dump.bin` из папки архива. `cpa_poc.py` не требует ни железа, ни дампа. Зависимостей вне стандартной библиотеки Python 3 нет
