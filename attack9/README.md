# Вектор 9 — извлечение ключа AES-256 анализом питания (CPA)

Ключ AES-256 залочен в OTP и недоступен через чтение, debug или глитч (stepping A4). Остаётся физический сторонний канал: загрузчик исполняет программный табличный AES mbedtls, поэтому корреляционный анализ питания (CPA) способен восстановить ключ из энергопотребления чипа во время расшифровки образа. Этот документ — план атаки и обоснование осуществимости, не выполненный PoC

## Вектор атаки и классификация

**Классификация:** физическая атака по стороннему каналу, CWE-1300 (Improper Protection of Physical Side Channels). Контрмер side-channel в сборке нет: `MBEDTLS_AES_ROM_TABLES` без constant-time, без аппаратного offload, без `*_ALT`

**Условия:** физический доступ к плате, точка съёма питания ядра или ЭМ-поля, управляемый reset. Debug и OTP-чтение не нужны — атакуется само вычисление AES. Детали версии и конфигурации mbedtls — в [`REPORT_RP2350.md`](../REPORT_RP2350.md), вектор В2

## Механизм

Загрузчик зовёт `decrypt` → `mb_aes_crypt_ctr_xor` → табличный `mbedtls_aes_crypt_ecb` (подтверждено в Ghidra, таблицы S-box и FT0 видны в дампе). Это не hardened `aes.S` из варианта на ассемблере, поэтому обращения к таблицам раунда создают зависящее от данных энергопотребление, которое и эксплуатирует CPA

Основной метод — last-round CPA по известному keystream:

- Keystream блока — это выход AES-ECB: `keystream_b = C_b XOR P_b`, где `C_b` — шифртекст из дампа, `P_b` — открытый текст блока. Из-за полной диффузии AES смена даже одного байта счётчика `nonce[15]` меняет все 16 байт выхода, поэтому last-round CPA восстанавливает все 16 байт round key 14
- Цепочка: last-round CPA → rk14 → second-round CPA (отпиливание rk14) → rk13 → инверсия key schedule AES-256 → мастер-ключ 256 бит
- Методология — O'Flynn, IACR eprint 2014/899, анализ питания AES-256 в загрузчике. Численная симуляция восстановила полный ключ
- Почему не first-round: наивный round-1 ECB CPA на этом устройстве даёт только ~2 байта (см. ниже), так как варьируется лишь вход. Last-round этого избегает — он опирается на полностью диффундированный выход

## Источники вариации и накопление статистики

Вход AES при каждой загрузке фиксирован: один образ, один публичный IV, `nonce0 = iv0 = IV_public XOR IV_salt`. Межблочная вариация `nonce[12..15] ^= BE(block_index)` при 3122 блоках partition B меняет лишь `nonce[15]` полностью и `nonce[14]` в диапазоне 0..12, а `nonce[12..13]` = 0

Отсюда ограничение first-round подхода: наивный round-1 ECB CPA восстанавливает только ~2 байта ключа (`14`, `15`), так как варьируется лишь вход, а застывшие входные байты дают нулевую корреляцию. Проверено софтовым PoC на синтетических трассах (модель HW(Sbox) + шум): 16/16 байт RK0 при варьируемом входе, но только 2 байта под ограничениями устройства

Last-round подход это обходит: его величина — выход ECB (keystream), а он диффундирован полностью, поэтому все 16 байт rk14 извлекаются даже при изменении одного `nonce[15]`. Статистика копится усреднением по множеству ресетов на каждый из нескольких известных блоков

> [!IMPORTANT]
> Единица накопления статистики — повторный boot, не следующий блок. Атака строится на тысячах автоматических ресетов по нескольким известным блокам keystream, а не на вариации chosen-plaintext

## Бюджет известного открытого текста

Last-round CPA требует несколько различных известных блоков keystream — оценочно около девяти:

- Блок 0 известен точно: векторная таблица приложения из утечки UART ([вектор 8](../attack8/README.md), SP `0x20082000`, reset `0x20000197`, NMI `0x2000011b`, HardFault `0x2000011d`)
- Остальные — предсказуемый Pico-crt0, дальше открытый текст неизвестен

> [!NOTE]
> До сборки стенда стоит проверить, нет ли в векторной таблице кастомных обработчиков: это уточняет, сколько блоков crt0 реально предсказуемы. Если различных известных блоков меньше шести, применяется запасной метод

## Стенд, триггер и захват

- Железо: ChipWhisperer Husky плюс шунт в рельс core VDD либо ЭМ-пробник. Decap не нужен. RP2350 Security Playground (2-е изд.) выводит линию питания ядра
- Триггер: UART "Pre decryption" (грубая синхронизация) или GPIO-хук (точная), далее выравнивание трасс по SAD
- Захват: тысячи ресетов на каждый известный блок для набора SNR, минуты-десятки минут при автоматическом reset
- Анализ: last-round CPA для rk14, затем second-round CPA для rk13, затем инверсия key schedule AES-256 (ChipWhisperer analyzer либо scared)

## Запасной метод — SPA или template по key schedule

Если различных известных блоков keystream меньше шести, last-round CPA недостаточно обеспечен данными. Тогда атакуется развёртка ключа `mbedtls_aes_setkey_enc` (`0x100037c8`), которая обрабатывает все 32 байта ключа независимо от входа. Точка утечки — вес Хэмминга байтов ключа при копировании и `HW(Sbox(key_byte))` в SubWord-шаге

Это не CPA: при фиксированном ключе `setkey` детерминирован, дисперсия нулевая, корреляция по трассам не строится. Нужен SPA или template-анализ, а для профиля — отдельный клон RP2350 с известным ключом. Путь input-независим, но дороже по оснастке

## Проверка восстановленного ключа

Оракул — один AES на проверку, без эвристики:

```text
keystream[0] = AES256_ECB_ENC(key, iv0),  iv0 = IV_public XOR IV_salt
IV_public = 921e94597201e138c2747ca1e1bd1b0b   (из образа @0x80014)
цель       = 4a5e4990642bb18272952f73b9854d09   (= CT[0:16] XOR PT[0:16])
```

Совпадение цели подтверждает ключ. Дальше образ расшифровывается офлайн дешифратором `scratchpad/decrypt_rp2350.py` (функция `decrypt_with_raw_key`)

## Оценка атаки

**Сложность эксплуатации: высокая** — нужен специализированный стенд захвата, точка съёма питания, автоматический reset и ограниченный known-plaintext. Оценка CVSS 3.1: `CVSS:3.1/AV:P/AC:H/PR:N/UI:N/S:U/C:H/I:N/A:N` — **4.2 (Medium)**

**Результат при успехе:** мастер-ключ AES-256, а значит офлайн-расшифровка всего образа приложения из дампа. Это единственный остаточный крипто-путь к ключу: офлайн-брутфорс и слабый-ключ закрыты отрицательными проверками (см. [`REPORT_RP2350.md`](../REPORT_RP2350.md)), глитчи закрыты на A4

### Как исправить

Собирать AES в constant-time или на аппаратном ускорителе без табличных обращений, включить детекторы глитчей и SCA-защиту питания, не оставлять табличный программный AES в защищённом загрузчике

## Статус

Документированный план, обоснованный по коду (Ghidra), конфигурации (mbedtls), методологии (O'Flynn 2014/899) и численной симуляцией, восстановившей полный ключ. Симуляция подтвердила: last-round CPA берёт все 16 байт rk14, а ограничение "только 2 байта" относится к first-round (фиксированный вход), не к основному методу. Стенд на живом железе не собран, реальные трассы не сняты. Контраст: hardened `aes.S` — отдельный незакрытый баунти RP Hacking Challenge 2, а здесь путь табличный, поэтому атака осуществима
