# PIN сейфа — 3952

Найден **обоими** предложенными способами; результат совпадает.

## Способ 1 — глубоко в бинарном коде

Проверка PIN целиком лежит в `board_gpio_init` (`0x10000ab0`) — там же, где опрос
энкодера. Как это устроено:

1. Энкодер крутится → значение цифры (сырое `0..9`, заворачивается `9→0` и `0→9`)
   пишется в стековый буфер `sp+0x34+idx` (`strb r3,[r2,r6]`, `r2=sp+0x34`).
   Кнопка энкодера → следующая цифра; на LED цифра показывается через
   таблицу сегментов `0x10005508` (`7 6 5 4 3 2 1 0 9 8`).
2. На **четвёртом нажатии кнопки** запускается верификация (`0x10000c72: cmp r6,#2; bhi …`):

```
10000C7E  mov  r5, r8            ; r8 = 0x100054FF (из пула DAT_10000e10, загрузка на 0x10000bf8)
10000C7C  movs r4, #1           ; индекс = 1
10000C82  add  r3, sp, #0x33
10000C86  ldrb r2, [r3, r4]     ; введённая цифра: sp+0x34+r4-1 = entered[0..3]
10000C88  ldrb r3, [r5, r4]     ; эталон: 0x100054FF + r4
10000C8A  cmp  r2, r3
10000C8C  bne  fail              ; ранний выход на первом несовпадении
10000C8E  movs r0, #0x32        ; 50 мс задержка/пик на каждую СОВПАВШУЮ цифру
10000C90  adds r4, #1
10000C92  bl   0x1000239c
10000C96  cmp  r4, #5
10000C98  bne  0x10000c82       ; все 4 цифры? (r4 = 1..4)
        ; успех:
10000CC2  ldr  r3, [pc, #0x150] ; -> 0x20002ED2
10000CC4  strb r2(=1), [r3]     ; unlock-флаг = 1  (USB MSC становится виден хосту)
```

3. Эталон лежит в rodata по адресу **`0x100054FF`**: байты `00 03 09 05 02`.
   Нулевой байт — dummy, сравнение идёт по индексам 1..4, то есть

   **PIN = `3 9 5 2`**

Других вхождений последовательности `00 03 09 05 02` в образе нет, и на
`0x100054FF` ссылается ровно один указатель (`DAT_10000e10`) — запасного PIN в
прошивке нет.

Замечание к «безусловному `tud_init` в `main`» (из общей памяти): USB-стек
действительно стартует всегда, но хост увидит флешку только после
`*(uint8_t*)0x20002ED2 = 1` — этот флаг и ставит проверка PIN. Трассировка
закрыта.

## Способ 2 — симуляция и брутфорс

[`pin_sim.py`](pin_sim.py) — точная симуляция проверочного цикла (эталон,
ранний выход, задержка на совпадение):

```
$ python3 pin/pin_sim.py
reference bytes @ 0x100054ff: 00 03 09 05 02
[sim] full 10^4 brute force: 1 accepted PIN(s): 3952
[sim] black-box side-channel attack: 40 dial attempts worst-case -> PIN 3952
[sim] verify(3952) -> unlocked=True
```

- полный перебор всех 10 000 кодов через симуляцию проверщика: принимается
  **ровно один** — `3952`;
- чёрный ящик: устройство даёт по **50 мс задержки на каждую совпавшую ведущую
  цифру** — время ответа раскрывает длину совпавшего префикса, поэтому на живом
  устройятии PIN снимается за **≤40 прокруток** (4 позиции × 10 цифр), без
  знания прошивки.

## Сопутствующие слабости (в духе attack1/2/3)

- **побайтовый ранний выход** + **задержка на совпадение** — классический
  timing/feedback оракул (см. скилл `firmware-analysis`, векторы 1 и 2);
- PIN хранится **открытым текстом в rodata** (`0x100054FF`) и извлекается из
  дампа так же, как ключ шифрования хранилища (CWE-321 по духу);
- PIN не участвует в криптографии (см. [`attack1`](../attack1/README.md)),
  так что знание PIN вообще не требуется для чтения данных — оно нужно только
  чтобы устройство само показало флешку хосту.

## Как проверить на живом устройстве

1. Включить сейф, крутить энкодер: LED показывает текущую цифру.
2. Выставить `3` → нажать кнопку энкодера → `9` → кнопка → `5` → кнопка →
   `2` → кнопка.
3. Индикатор успеха — длинное «успешное» мигание (в прошивке после 4-й цифры
   пишется `0x400` в GPIO OUT и ставится флаг `0x20002ED2`); флешка появится
   на хосте как USB Mass Storage.
