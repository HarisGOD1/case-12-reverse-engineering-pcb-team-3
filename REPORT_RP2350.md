# Отчёт этапа 2 — реверс кибер-сейфа на RP2350

Этот документ собирает итоги второго этапа трека Positive Technologies на ЛЦТ 2026 в один сдаваемый отчёт. Источники — рабочая сводка [`drafts/STAGE2_RP2350_HANDOFF.md`](drafts/STAGE2_RP2350_HANDOFF.md) и отчёт по живому вектору [`attack8/README.md`](attack8/README.md). История прошлого этапа (RP2040) — в общей памяти [`.claude/memory/lct-2026-usb-token-reverse.md`](.claude/memory/lct-2026-usb-token-reverse.md), к новому железу она напрямую не применима

## Резюме

Новое устройство — RP2350, а прошивка в дампе — апстримный пример `enc_bootloader` из pico-examples, не прошлогодний `usb_token`. Прошлогодний класс атак (офлайн-дешифровка образа из флеш-дампа, CWE-321) закрыт системно: ключ AES-256 вынесен в OTP и залочен на чтение, добавлены secure boot и собственная подпись. Из одного `firmware_dump.bin` расшифровать образ приложения нельзя — нужен ключ из OTP, а он достаётся только физической атакой по кристаллу

Загрузчик сверен с чистым апстримом по декомпиляции — модификаций и бэкдора нет. Единственная уязвимость, подтверждённая на живом железе без ключа, — утечка первых 16 байт расшифрованного образа через отладочный UART (Debug-сборка). Главный остаточный путь к ключу — физический анализ питания (CPA) по табличному AES, не закрытый степпингом A4. Остальное — инвазивная fault injection и конфигурационные слабости

> [!NOTE]
> Главный вывод этапа — защита данных приложения на RP2350 устойчива к офлайн-атакам прошлого года. Остаточные риски лежат в плоскости физических атак по стороннему каналу и fault injection, а не программной криптографии

## Устройство и образ

- Чип RP2350 (Cortex-M33, ARMv8-M), плата RP2350 Zero. Маркировка корпуса `RP2350A0A4` — корпус A (QFN-60), stepping A4. SRAM 520 КиБ (`0x20000000..0x20082000`), база XIP-флеш `0x10000000`, объём 4 МиБ
- Stepping A4 (не A2) закрыл challenge-глитчи E16/E20/E21/E24 через фикс boot ROM и OTP-враппера (по Raspberry Pi PCN и WOOT'25, первоисточники в этой сессии не перепроверялись). Неинвазивный глитч-путь к ключу OTP недоступен, остаётся FIB/PVC уровня IOActive
- Serial живого чипа `8295FF712987C1CA`, на момент снятия — в режиме BOOTSEL (`USB 2e8a:000f RP2350 Boot`)
- Прошивка — `enc_bootloader` (pico-examples, ветка master, вариант на mbedtls). SDK 2.3.1, собрано 9 окт 2026, конфигурация Debug, автор по пути сборки — `C:/Users/dsokolov/...`
- Образ исполняется из SRAM: boot ROM копирует `0x10000000..0x10007530` в `0x20070000`, точка входа `0x20070197`, SP `0x20082000`

## Карта дампа firmware_dump.bin (база XIP 0x10000000)

| Смещение флеш | Содержимое |
| --- | --- |
| `0x0..0x7530` | `enc_bootloader` — код, vector table, picobin-метаблоки на `0x15c`, `0x700`, `0x7530`, `0x75a4` |
| `0x5000..0x7200` | таблицы mbedtls AES (S-box `0x718c`, inv-S-box `0x608c`, T-table FT0 `0x6d8c`) — не ключ |
| `0x8200..0x7ffff` | `0xFF`, включая partition A (пустая) |
| `0x80000..0x8cfff` | partition B — зашифрованный образ приложения |
| `0x8d000..0x2fffff` | `0xFF` |
| `0x300000..0x3065ff` | непрозрачный блоб 26112 байт (назначение не установлено) |
| `0x306600..0x3ffdff` | `0xFF` |
| `0x3ffe00..0x3fffff` | ещё блоб 512 байт (назначение не установлено) |

Партиции A/B: A `0x10000..0x80000`, B `0x80000..0xf0000`. Активна B, A пустая

## Крипто-схема

Схема подтверждена по исходнику апстрима и автономными самотестами дешифратора:

- AES-256-CTR, 14 раундов, keystream = AES256-ECB-ENC(nonce)
- `iv0 = IV_public XOR IV_OTPsalt` — побайтовый XOR 16 байт
- Инкремент счётчика нестандартный: для блока k берётся `nonce = iv0`, затем `nonce[12..15] ^= big-endian u32(k)` — XOR, не сложение, старшие 12 байт неизменны
- Ключ — 4-way XOR share в OTP page 29-30 (192 байта: слова 0..15 в key[0..3], слова 16..31 — пустышка-дыра FIB, слова 32..47 в key[4..7])
- Соль IV — OTP page 31 (16 байт)
- Дешифратор `scratchpad/decrypt_rp2350.py` автономен, содержит свой AES-256, все самотесты прошёл. Функции `reconstruct_key`, `make_iv0`, `ctr_xor_decrypt`, `decrypt_image`, `decrypt_with_raw_key`

Структура зашифрованного образа в partition B разобрана побайтово: start marker `0xffffded3` на `0x80000`, end marker `0xab123579` на `0x80010`, публичный IV на `0x80014` = `921e94597201e138c2747ca1e1bd1b0b`, шифртекст на `0x80024` размером `0xc320` (49952 байта, 3122 блока по 16)

## OTP и secure boot

Снято с живого устройства через picotool в режиме read-only. Залочены на чтение и в guarded, и в raw (оба дают `XXXXXXXX`): page 29, 30 (ключ), 31 (соль), 48, 49 (хэши BOOTKEY), 62, 63. Остальной OTP читается. Raw-режим лок не обходит

Конфигурация secure boot (CRIT1 = `0x7`):

| Параметр | Значение | Смысл |
| --- | --- | --- |
| `SECURE_BOOT_ENABLE` | 1 | проверка подписи образа включена |
| `DEBUG_DISABLE` | 1 | весь debug, включая SWD, закрыт |
| `SECURE_DEBUG_DISABLE` | 1 | secure-debug закрыт |
| `GLITCH_DETECTOR_ENABLE` | 0 | аппаратные детекторы глитчей не включены |

`BOOT_FLAGS0` = `0x0`: PICOBOOT и MSD открыты, `DISABLE_WATCHDOG_SCRATCH` = 0 (паллиатив против reboot-глитча не выставлен). `BOOT_FLAGS1` KEY_VALID = 1. Anti-rollback неактивен: `DEFAULT_BOOT_VERSION` = 0 (OTP rows `0x4e-0x53` нулевые), `ROLLBACK_REQUIRED` = 0. Ключ подписи заменён на собственный, не демонстрационный: публичный ключ устройства `8B2316D5...` против демо-ключа примера `61826D31...`

## Результат разведки в Ghidra

Программа `firmware_dump.bin` размечена в общем Ghidra-проекте (язык `ARM:LE:32:Cortex`, байты образа не тронуты). Образ слинкован под исполнение из SRAM `0x20070000`, а в дампе лежит по базе флеш `0x10000000`, смещение ровно `0x10070000`: прямые `BL`-вызовы и чтения XIP разрешаются корректно, абсолютные литералы-указатели `0x2007xxxx` указывают на SRAM

Главные выводы разведки:

- Прошивка — немодифицированный `enc_bootloader`. Функции `main`, `decrypt`, `mb_aes_crypt_ctr_xor`, `mbedtls_aes_crypt_ecb`, `lock_key` сверены с апстримом по декомпиляции, логика совпадает. Авторских модификаций и бэкдора нет. Ключ читается из OTP guarded (`0x40138E80` page 29, `0x40138F80` page 31), в коде его нет
- Дешифратор зовёт `mb_aes_crypt_ctr_xor`, то есть табличный программный `mbedtls_aes_crypt_ecb`, а не hardened `aes.S` — это и открывает путь для CPA (вектор В2)
- Утечка в UART подтверждена прямо в `main`: `puts("Post decryption image begins with")` и четыре `printf("%08x")` печатают первые 16 байт расшифрованного образа в UART0 TX
- Блоб `0x300000` и хвост `0x3ffe00` загрузчиком не используются: выровненных литералов `0x10300000` / `0x103ffe00` в коде нет, `main` читает только активную партицию B через ROM API, не хардкодом
- Проверки размера в `memcpy` помечены `todo harden`: максимум DoS или крах, не RCE — `rom_chain_image` перепроверяет подпись расшифрованного образа (вектор В10)

## Крипто-библиотека mbedtls в сборке

- Версия: pico-sdk 2.3.1 пинит сабмодуль `lib/mbedtls` точно на **mbedtls 3.6.6** (коммит `0bebf8b8c7f07abe3571ded48a11aa907a1ffb20` от 2026-03-26, upstream `Mbed-TLS/mbedtls`, sha совпадает с тегом `v3.6.6` побайтно). Это релиз, не промежуточный коммит
- Конфигурация `mbedtls_config.h` в `bootloaders/encrypted/`: включены `MBEDTLS_HAVE_ASM`, `MBEDTLS_AES_C`, `MBEDTLS_AES_ROM_TABLES`, `MBEDTLS_CIPHER_MODE_CTR`. `MBEDTLS_AES_FEWER_TABLES`, `MBEDTLS_AES_USE_HARDWARE_ONLY` и любые `MBEDTLS_*_ALT` отсутствуют — табличный программный AES, без constant-time альтернатив, без аппаратного offload. Контрмер side-channel в mbedtls-части нет
- `mbedtls_aes.c` в самом примере — это не реализация AES, а обёртка `mb_aes_crypt_ctr_xor()` самодельного CTR, которая зовёт `mbedtls_aes_crypt_ecb(ctx, MBEDTLS_AES_ENCRYPT, ...)` в цикле. Используется только путь encrypt, decrypt-путь mbedtls не вызывается вовсе
- 4-way XOR-share ключа в `decrypt()` (комментарий кода "due to the FIB workaround") — маскирование против fault injection, не против тайминга

Известные CVE версии 3.6.6 по AES, setkey, side-channel, разобранные на применимость:

| CVE | Суть | Применимость к сборке |
| --- | --- | --- |
| CVE-2025-52496 | race в детекции AESNI, извлечение AES-ключа в многопотоке на x86 с AESNI | нет — пофикшено до 3.6.6, и нет x86/AESNI/многопоточности |
| CVE-2025-59438 | padding-oracle по таймингу | нет — пофикшено до 3.6.6, и в CTR нет padding |
| CVE-2025-54764 | локальная timing-атака на RSA | нет — пофикшено до 3.6.6, RSA в загрузчике не используется |
| CVE-2025-66442 | compiler-induced timing side channel в RSA и CBC/ECB decrypt при сборке clang/LLVM с select-optimize | формально версия подпадает, практически нет — тулчейн `arm-none-eabi-gcc`, не LLVM, и decrypt-путь не вызывается |

Классическая cache-timing атака на табличный AES (Bernstein-класс) — это не CVE, а задокументированное ограничение table-based AES. В данном сценарии она неприменима: Cortex-M33 в этой конфигурации без data cache (нет hit/miss-канала), атакующий не может исполнить свой код (SWD закрыт, A4 закрыл boot ROM глитчи), AES крутится при загрузке и не является оракулом для множества запросов с контролем входа. Программный side-channel к ключу не ведёт — не из-за защиты mbedtls, а из-за отсутствия физических предпосылок. Физический же канал (питание, вектор В2) этим выводом не закрывается

## Уязвимости и векторы

Для каждого вектора указан класс угрозы CWE и базовая метрика CVSS 3.1. Векторы упорядочены по реальной эксплуатируемости на данном устройстве (stepping A4, debug закрыт). Оформление класса угрозы повторяет секцию "Класс угрозы" в [`attack8/README.md`](attack8/README.md)

### В1 — утечка начала образа через отладочный UART (подтверждён на железе)

Debug-сборка `enc_bootloader` печатает первые 16 байт расшифрованного образа приложения в UART0 TX (GP0) при каждой загрузке, до передачи управления. Имея физический доступ к UART, атакующий читает эти байты без ключа. В режиме CTR блоки гаммы независимы, поэтому утечка первого блока не раскрывает остальные. В исследованном образе эти 16 байт — штатная векторная таблица Cortex-M (SP `0x20082000`, reset `0x20000197`, NMI `0x2000011b`, HardFault `0x2000011d`), секрета в них нет. Ценность вектора — доказательство утечки и known-plaintext для блока 0, не раскрытие ключа

- Класс угрозы: CWE-1295 "Debug Messages Revealing Unnecessary Information". Близкие классы — CWE-215 "Insertion of Sensitive Information Into Debugging Code", CWE-200 "Exposure of Sensitive Information to an Unauthorized Actor"
- CVSS 3.1: `AV:P/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N`, базовый балл 2.4 (Low)
- Статус: подтверждён на живом RP2350 через второй RP2040 с прошивкой debugprobe (GP5 RX ← GP0 TX, общая земля, 115200 8N1). Захваченные слова побайтно совпали с шифртекстом в дампе по смещению `0x80024`. Отчёт и артефакты — [`attack8/`](attack8/)

### В2 — CPA по стороннему каналу питания на табличный AES (главный путь к ключу)

Загрузчик исполняет программный табличный `mbedtls_aes_crypt_ecb` (`MBEDTLS_AES_ROM_TABLES`, без constant-time и без аппаратного offload), а не hardened `aes.S` — подтверждено в Ghidra. Это открывает атаку по мощности на табличный AES. Важная оговорка по методу: вход AES при каждой загрузке фиксирован (один образ, один IV, `nonce0 = iv0`), поэтому классический CPA с варьируемым известным plaintext напрямую неприменим. Вариация есть только между блоками одного boot — `nonce[12..15] ^= BE(k)` меняет 4 младших байта счётчика на 3122 блоках, — поэтому атака опирается на межблочную вариацию либо на DPA по шуму при фиксированном входе. Степпинг A4 закрыл глитчи, но физический side-channel по питанию он не закрывает, а `GLITCH_DETECTOR_ENABLE` = 0 и отсутствие SCA-контрмер в сборке только облегчают захват трасс. Детальный playbook готовит смежная сессия

- Класс угрозы: CWE-1300 "Improper Protection of Physical Side Channels"
- CVSS 3.1: `AV:P/AC:H/PR:N/UI:N/S:U/C:H/I:N/A:N`, базовый балл 4.2 (Medium)
- Статус: путь обоснован по коду, не выполнялся на железе; требует осциллограф или ChipWhisperer, изоляцию рельса питания и сбор трасс

### В3 — открытый PICOBOOT/MSD через BOOTSEL

`BOOT_FLAGS0` = `0x0` оставляет PICOBOOT и MSD открытыми: через BOOTSEL возможно неавторизованное чтение и запись всей 4-МиБ флеш без проверки секьюрности. Чтение снимает полный дамп (так и получен `firmware_dump.bin`). Запись позволяет затереть хранилище `0x300000` или испортить партиции. Secure boot этим не пробивается — подмену исполняемого образа проверка подписи отклонит

- Класс угрозы: CWE-1299 "Missing Protection Mechanism for Alternate Hardware Interface". Близкий класс — CWE-284 "Improper Access Control"
- CVSS 3.1: `AV:P/AC:L/PR:N/UI:N/S:U/C:L/I:L/A:L`, базовый балл 4.3 (Medium)
- Статус: чтение подтверждено (дамп снят), запись не выполнялась

### В4 — voltage glitch для re-enable debug и чтения ключа OTP (E16, закрыт на A4)

Просадка питания в окне после guard-read PSM может вернуть debug и открыть чтение OTP page 29-31 с последующей офлайн-дешифровкой. На stepping A4 этот путь закрыт фиксом boot ROM и OTP-враппера, поэтому на данном устройстве он теоретический и требует инвазивного FIB/PVC

- Класс угрозы: CWE-1247 "Improper Protection Against Voltage and Clock Glitches"
- CVSS 3.1: `AV:P/AC:H/PR:N/UI:N/S:U/C:H/I:N/A:N`, базовый балл 4.2 (Medium)
- Статус: закрыт на A4, подтверждения на железе нет

### В5 — reboot-API glitch для исполнения своего кода до sw_lock (E20, закрыт на A4)

Глитч в окне reboot-API позволяет исполнить свой код до блокировки страниц ключа (`lock_key`), payload — дампер OTP в UART. `DISABLE_WATCHDOG_SCRATCH` = 0 оставляет паллиатив невыставленным. На A4 путь закрыт тем же фиксом boot ROM

- Класс угрозы: CWE-1247 "Improper Protection Against Voltage and Clock Glitches"
- CVSS 3.1: `AV:P/AC:H/PR:N/UI:N/S:U/C:H/I:N/A:N`, базовый балл 4.2 (Medium)
- Статус: закрыт на A4, подтверждения на железе нет

### В6 — laser fault injection (E24, инвазивный)

Лазерный впрыск ошибки после decap кристалла. Дорого, требует вскрытия корпуса и оборудования уровня IOActive, не первый выбор

- Класс угрозы: CWE-1319 "Improper Protection against Electromagnetic Fault Injection (EM-FI)"
- CVSS 3.1: `AV:P/AC:H/PR:N/UI:N/S:U/C:H/I:N/A:N`, базовый балл 4.2 (Medium)
- Статус: не выполнялся

### В7 — конфигурационная слабость, облегчающая fault injection и SCA

Аппаратные детекторы глитчей выключены (`GLITCH_DETECTOR_ENABLE` = 0), паллиатив `DISABLE_WATCHDOG_SCRATCH` не выставлен. Сам по себе вектор ключ не извлекает, но снижает сложность векторов В2 и В4-В6: устройство оставлено максимально податливым к физическим атакам при включённом secure boot

- Класс угрозы: CWE-1247 "Improper Protection Against Voltage and Clock Glitches". Близкий класс — CWE-1188 "Initialization of a Resource with an Insecure Default"
- CVSS 3.1: `AV:P/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:N`, базовый балл 0.0 — прямого воздействия нет, вектор усиливающий
- Статус: конфигурация снята с живого устройства

### В8 — anti-rollback неактивен (латентная слабость)

`DEFAULT_BOOT_VERSION` = 0 и `ROLLBACK_REQUIRED` = 0: номер версии безопасности не выставлен и откат не запрещён. Партиция A пустая, но загружаемая. Сам по себе вектор ничего не вскрывает, но при утечке любого ранее подписанного образа ничто в OTP не помешает откату на уязвимую версию

- Класс угрозы: CWE-1328 "Security Version Number Mutable to Older Versions"
- CVSS 3.1: `AV:P/AC:H/PR:N/UI:N/S:U/C:N/I:L/A:N`, базовый балл 2.0 (Low)
- Статус: конфигурация снята с живого устройства, эксплуатация требует предусловия (подписанный старый образ)

### В9 — отсутствие TrustZone-ACL на партициях (латентная слабость)

Все партиции и unpartitioned-область помечены NS(rw) (из `enc-pt.json` и picotool): нет secure-only ACL TrustZone. Хранилище `0x300000` защищено только шифрованием, без defense-in-depth. Нарушение разделения ресурсов, усиливает последствия любого доступа к флеш

- Класс угрозы: CWE-1189 "Improper Isolation of Shared Resources on System-on-a-Chip (SoC)"
- CVSS 3.1: `AV:P/AC:H/PR:N/UI:N/S:U/C:L/I:N/A:N`, базовый балл 2.0 (Low)
- Статус: конфигурация снята с живого устройства

### В10 — отсутствие проверки размера в memcpy (DoS, низкая)

В `main` проверки размера при копировании в SRAM помечены `todo harden`. Последствие ограничено крахом или DoS: `rom_chain_image` перепроверяет подпись расшифрованного образа, поэтому RCE через этот путь не достигается

- Класс угрозы: CWE-120 "Buffer Copy without Checking Size of Input"
- CVSS 3.1: `AV:P/AC:H/PR:N/UI:N/S:U/C:N/I:N/A:L`, базовый балл 2.0 (Low)
- Статус: обосновано по коду, эксплуатация не выполнялась

## Что проверено с отрицательным результатом

- Брутфорс ключа и соли невозможен: AES-256 плюс 128-битная соль
- Слабый ГСЧ ключа: дефолтные ключи примера, нулевые, `0xFF`, паттерны — ни один не даёт правдоподобный образ RP2350. Ключ — настоящий OTP-секрет
- Ключ и соль как функция публичного chip serial: 16 KDF-кандидатов (sha256/sha512/md5 в обоих порядках байт, с солью и без, с префиксами) — ни один не валиден
- Широкий перебор человеческого ключа: 23934 проверки (3989 ключей × 6 солей) по точному оракулу на `keystream[0]`. Осмысленные строки, составные токены, байтовые паттерны, демо-ключ, оба chip-id, соли zero/`0xFF`/демо/serial/IV_public — ни одна не совпала. Ключ — настоящий случайный OTP-секрет
- Reuse keystream между областями отсутствует: `XOR(ct_partitionB, blob@0x300000)` даёт энтропию 7.96, гамма не общая. Блоб `0x300000` и хвост `0x3ffe00` своего IV-заголовка не имеют, статистически не отличимы от случайных
- OTP page 29/30 (ключ) и 31 (соль) — сплошные `XXXXXXXX` и в guarded, и в raw дампе. Секрета в снятом OTP нет
- Known-plaintext атака на CTR не продвигает расшифровку: с живого устройства сняты первые 16 байт расшифрованного образа (vector table приложения), `keystream[0] = CT XOR PT`. В CTR keystream блока 0 не даёт keystream блоков 1+ без ключа
- Программный side-channel mbedtls (cache-timing) к ключу не ведёт: нет data cache, нет исполнения своего кода, AES не оракул (см. секцию mbedtls). CVE 3.6.6 по AES/RSA неприменимы
- `SECURE_PARTITION_TABLE` и `HASHED_PARTITION_TABLE` = 0 инертны: таблица и так под подписью загрузчика. Блоки `extra_security` block1 против block3 — штатная структура, не слабость
- Подпись демо-ключом — нет, ключ заменён на собственный
- Перепаять OTP нельзя: это antifuse внутри кристалла RP2350, не отдельный чип, в отличие от прошлогодней внешней QSPI-флеш. Физический доступ к OTP — только decap плюс FIB/PVC
