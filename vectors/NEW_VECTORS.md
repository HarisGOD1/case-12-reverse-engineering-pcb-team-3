## Ответ на открытый вопрос hypotheses.md («ни прошивка, ни PIN»)

Самые дешёвые пути получить хранилище, не анализируя прошивку и не зная PIN:

1. **V15** — инжекция квадратурных импульсов в энкодер: брутфорс 10⁴ кодов без блокировки, внешний Pico за минуты; PIN не нужен как знание, только как цель перебора (attack4 уже делает это эмулятором).
2. **V9** — глитч единственного сравнения: PIN вообще не участвует, успех = один байт флага.
3. **V11 + глобальный PIN** — ✓ PIN `3952` зашит в образ и одинаков у всех плат: флешку жертвы достаточно переставить в **любой второй такой же сейф** и ввести известный с него PIN. Ни реверса, ни дампа, ни брутфорса — только паяльная станция.
4. **V1 (с оговоркой)** — оракул гаммы не требует ни прошивки, ни знания PIN, но требует **одной** разблокированной сессии (гость, оставленный без присмотра): дальше весь том расшифровывается офлайн навсегда.

## A. Хост как атакующий (без вскрытия корпуса)

### V1 — Оракул гаммы из «свободных» секторов диска ★ главная новая находка

✓ `msc_read10_decrypt_storage` (`0x10000354`) ограничивает LBA так: `param_2 < 0x800` — устройство отдаёт **2048 секторов = 1 МиБ**. Но зашифрованное хранилище занимает только **704 КиБ** (`0x10100000–0x101B0000`, 1408 секторов). Секторы 1408–2047 читаются из **стёртой флешки (0xFF)** и после «расшифровки» уходят на хост как `keystream XOR 0xFF` — то есть **чистая гамма, перевёрнутая побитно, легально отдается любому смонтировавшему диск хосту**.

✓ В дампе: область `0x101B0000–0x101FFFFF` (448 КиБ) — нули `0xFF`, и BPB тома тоже заявляет 2048 секторов — «свободное место» тома и есть окно оракула.

Важно: в отличие от гипотезы 6 из [`hypotheses.md`](../hypotheses.md) (обход через переполнение), здесь **никакого обхода не нужно** — прямое сравнение `param_2 < 0x800` пропускает эти LBA честно; баг в том, что граница объявлена по размеру тома (1 МиB), а не по размеру шифрованной области (704 КиБ). Проверку их гипотезы о CARRY4-обходе в область кода это тоже закрывает: первый `if` режет LBA ≥ 0x800 до всякой арифметики переноса.

Сценарий: один любой доступ к разблокированному диску (легальный гость, злонамеренный хост) → чтение свободных секторов → 448 КиБ чистой гаммы → восстановление параметров генератора `s = L*A + seed + j*B` как LCG (классическая задача, структура 32 блоков на сектор известна из дескриптора диска) → экстраполяция гаммы на **все** LBA → **офлайн-расшифровка всего хранилища из любого снимка флешки — без дампа прошивки, без анализа кода, без знания PIN**. Это суть attack3 («слабый шифр»), но поднятая с уровня «нужен реверс прошивки» до уровня «нужен один mount». Плюс правило: `A = 0x38C9CDA0` чётное → по чистой математике возможны дальнодействующие повторы гаммы (см. V24).

### V2 — Chosen-plaintext через write10

✓ `msc_write10_encrypt_storage` (`0x1000053c`) — то же преобразование, XOR сам себе обратен. Однократный доступ на запись → записать маркерные секторы → прочитать → мгновенная верификация гаммы по позициям. Комбинируется с V1: даже если свободные секторы когда-нибудь «закроют», выбранный открытый текст даёт тот же оракул. Отдельный подслучай — запись в свободные секторы **портит оракул для последующих атакующих** (гамма там уже не соответствует 0xFF) — заодно это идея защиты.

### V3 — Фаззинг SCSI/BOT-транспорта

✓ Колбэки принимают `param_3 < 0x200` (длина блока) — частичная валидация есть, но сам transport-слой TinyUSB остаётся фаззинг-поверхностью: аномальные CBW, `dCBWDataTransferLength` ≠ ожидаемому, смена LUN, операции вне READ/WRITE (FORMAT UNIT, UNMAP, TEST UNIT READY) — crash/DoS/рассинхронизация. ? Версия TinyUSB в прошивке неизвестна — стоит снять и сверить с историей CVE по msc_device; у TinyUSB были переполнения в MSC-обработке. Успешная memory corruption на M0+ (нет ни PAC, ни BTI) → исполнение кода от имени хоста без физики.

### V4 — Control transfer и строковые дескрипторы

? `tud_descriptor_string_cb` (`0x100008d4`) обслуживает запросы строк: индексы beyond range, экзотические LANGID — классика фаззинга дескрипторов. Слабая отдача (panic-строки есть), но дешёвая проверка на DoS/утечку.

### V5 — «Шифровальщик» на базе V2 (эволюция attack2)

Тот же легальный канал записи, но цель — не подмена содержимого, а **вымогательство**: перезашить хранилище гаммой с константами атакующего → владелец теряет доступ ко всему сейфу. Из attack2 (целостность) вырастает availability-вектор с денежным мотивом; CVSS-логика та же (S:C при выходе на хост).

### V6 — Вредоносный хост как источник глитча (VBUS)

Злоумышленник — это USB-порт, к которому владелец сам воткнул сейф. Просадки/броски VBUS в момент выполнения проверки PIN или записи флага → fault injection **через кабель**, без иглы и осциллографа. Успешность на M0+ правдоподобна: критический путь — одна команда записи байта-флага.

### V7 — Трекинг устройства

✓ iSerialNumber = `123456` (`0x1000537c`, одинаков для всех плат сборки — teammate-память). Любой хост, к которому подключали сейф, оставляет серийник в журналах/реестре ОС → корреляция владельца и перемещений. Приватность, не доступ; бесплатный OSINT-хвост для отчёта.

## B. Аппаратные векторы

### V8 — SWD: живая разблокировка и модификация SRAM

RP2040 не блокирует debug-порт по умолчанию, secure boot отсутствует ✓. ? На плате могут быть test pads под SWCLK/SWDIO — если да: подключение к **работающему** устройству → прочитать `*(uint8_t*)0x20002ED2`, записать `1` → MSC поднимается без PIN; плюс живой дамп SRAM (буферы, флаги, стек) и постановка на halt в произвольной точке. Это самая дешёвая «полная победа» при наличии пинов — стоит просто осмотреть плату.

### V9 — EMFI/клектовое глитчинг одиночного сравнения

✓ Проверка PIN — побайтовый цикл с ранним выходом (`bne fail` на `0x10000c8c`), успех — запись **одного байта** флага. Единственный CMP+branch на критическом пути — хрестоматийная цель для электромагнитной/_voltage-глитч-инъекции: пропуск ветки неудачи → разблокировка с неверным PIN. M0+ не имеет ни branch-защиты, ни детектора глитча. Для отчёта: показать, что защита сводится к одной команде.

### V10 — QSPI-интерсептор (MITM на флешке)

✓ Флешка внешняя (W25Q16, QSPI). Паяльный интерсептор между чипом и MCU: пассивно — лог всех чтений/записей (реальные секторы + расшифрованные? нет — расшифровка в MCU; но шина даёт шифротекст и адреса → база known-plaintext для attack3 без всякого реверса); активно — подмена содержимого «на лету» сильнее, чем офлайн-запись из attack2, и позволяет логировать поведение прошивки как отладчик.

### V11 — Transplant/chip-off без анализа прошивки

Пересадить флешку жертвы на **свой** такой же сейф: прошивка идентична, гамма та же → расшифровка у себя, никакого реверса и дампов. Вариант attack1/3 «для людей без Ghidra»; отдельно — чип читается программатором за минуты.

### V12 — Цепочка «BOOTSEL-провал»: постоянная дверь обслуживания

Bootrom RP2040 входит в USB-режим Mass Storage (полный доступ ко всей флешке, 2 МиБ, без PIN), если загрузка из флеша не прошла (например, битый CRC boot2). Злонамеренная maid-запись пары байт в boot2 (attack2-канал или V10) → устройство **навсегда** стартует в незащищённый bootrom-MSD: «сломали — и этим открыли». Готовый вектор превращения разового доступа в постоянный.

✓ Попутно: в текущем образе сохранённый CRC boot2 `0x7A4EB274` ≠ CRC32 первых 0xFC байт (`0xD4A3FD6A`) — аномалия уже зафиксирована в `reversing/`; вероятно другой вариант CRC (MPEG-2 и т.п.), но она заслуживает явной проверки, см. V22.

### V13 — Второе ядро

✓ В прошивке ядро 1 не используется (весь код однопоточен на core0). Через SWD (после V8) можно запустить свой код на core1 **параллельно** честному выполнению: гонять SIO FIFO/периферию, снимать состояние в момент проверки PIN, не останавливая устройство. Экзотика, но бесплатный аргумент «two cores — twice the surface».

### V14 — Переживание флага разблокировки через тёплый перезапуск

✓ Флаг `0x20002ED2` пишется только при успехе PIN и читается `app_led_task`; явного обнуления в `board_gpio_init` нет (обнуляются соседние флаги `0x20002ED0/ED1` и буфер ввода). ? Если флаг в `.bss`, crt0 занулит его на любом рестарте — вектор закрывается; если в нетронутой SRAM (или crt0 затирает только часть), то быстрый reset/reset-pin после разблокировки владельцем → устройство стартует с флагом=1 → USB виден без PIN. Проверка — один эксперимент: читать байт по `0x20002ED2` через SWD до/после warm reset.

## C. Человек и PIN

### V15 — Инжекция импульсов в линию энкодера

✓ Энкодер — GPIO 27/28/29 (teammate-память), опрос программный, **блокировки перебора нет**. Щуп/крокодил на дорожки (или test pads) → синтетические квадратурные импульсы + нажатия → автоматический перебор 10⁴ кодов за минуты на живом устройстве, без знания прошивки. Аппаратный брутфорс как сервис. Реализацию см. [`attack4/`](../attack4/) — Pico-эмулятор энкодера от коллеги; здесь добавляется вариант без эмулятора: прямая инжекция в существующие дорожки платы.

### V16 — Акустический оракул бипов

✓ На каждую совпавшую ведущую цифру — задержка 50 мс (`FUN_1000239c(0x32)`, см. `pin/`); устройство пищит/мигает. Запись на диктофон с другого конца стола → длина успешного префикса → направленный перебор ≤40 попыток. Атака из `pin/`, но с носителем «звук» — работает даже без прямой видимости индикатора.

### V17 — Видеоплечо

✓ LED показывает текущую цифру при наборе (таблица сегментов `0x10005508`) + отдельная анимация успеха. Камера наблюдения/видеозвонок/отражение → PIN восстановлен пассивно. Ноль инструментов, ноль следов.

### V18 — Судебная экспертиза износа

Классика банкоматов: самый используемый сектор энкодера/кнопки выдает позицию(и) PIN. Слабо формализуемо, но бесплатно и эффектно для демо.

### V19 — ЭМ-излучение опроса энкодера

Ближняя зонная катушка на GPIO-опрос (`app_led_task`/`board_gpio_init` крутят SIO `0xd0000014/18`) → восстановление набираемых цифр дистанционно. Развитие V16/V17 в TEMPEST-сторону; трудоёмко, но закрывает «пассивную дистанционную» нишу.

### V20 — Бэкдор в PIN через запись во флеш

При любом канале записи во флеш (attack2/V10/V12) — не ломать проверку, а **тихо дописать второй допустимый код**: подменить эталон `0x100054FF` или пропатчить цикл сравнения. Владелец пользуется своим PIN, maid входит своим. Стелс-вариант evil-maid, заметить можно только байтовой диффом образа.

## D. Прошивка и поставка

### V21 — Полная подмена прошивки

✓ Bootrom не проверяет подпись образов (RP2040). Любой канал записи (V10/V12/физическая) → своя прошивка: логирует набираемый PIN в скрытый сектор, открывается по «магическому» жесту, поднимает MSC без PIN или играет BadUSB-HID от имени флешки. Отличие от attack2: подменяется не содержимое сейфа, а **сам хранитель**; обратимо обнаружить сложнее — нужен оффлайн-хэш эталонного образа.

### V22 — Разобраться с аномалией boot2 CRC

✓ Уже замечено: сохранённый CRC ≠ вычисленный стандартным CRC32. Гипотезы: (а) другой алгоритм/инверсия — норма; (б) boot2 правлен после сборки — чей-то имплант или элемент задания. Один скрипт с перебором CRC-вариантов закрывает вопрос; если (б) — это отдельный готовый «вектор поставки» в отчёт.

### V23 — «Обновление прошивки» как социальная инженерия

Прошивки обновления у игрушки нет ✓ — и именно поэтому любое «исправленное ПО от производителя» владелец зальёт руками через BOOTSEL. Фишинговый билд с V21-имплантом доставляется без единого бита физического доступа.

## E. Крипто-надстройки над attack3

### V24 — Арифметика периода гаммы

`A = 0x38C9CDA0` делится на 2⁵ → `s(L)` повторяется с периодом 2²⁷ по L — внутри 1-МиБ диска коллизий нет, и это стоит зафиксировать в отчёте как «почему наивный reuse не работает». Но если когда-нибудь ослабят границу LBA (V1/V3) или изменят базу — дальнодействующие коллизии появятся автоматически: конструкция держится только на удачно коротком диске.

### V25 — Старший байт как побайтовый оракул и клоны

Гамма берётся **только старшим байтом** `(s + C_i) >> 24`: один байт гаммы на 16 байт данных, остаток 32-битного состояния не используется — сжатие энтропии в 16 раз, идеально для верификации V1/V2 по коротким маркерам. Плюс ✓ константы зашиты в образ → все платы сборки шифруют одинаково: расшифровка чужого сейфа своей платой (без Ghidra вообще).
