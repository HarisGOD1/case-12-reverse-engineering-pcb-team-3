Трек Positive Technologies на ЛЦТ 2026 — получить доступ к прошивке кибер-сейфа и описать уязвимости. Эта память общая для команды, лежит в репозитории; приватное и личное сюда не пишем.

## Устройство

Кибер-сейф на **Raspberry Pi RP2040** (двухъядерный Cortex-M0+, в Ghidra `ARM:LE:32:Cortex`, база XIP `0x10000000`), bare-metal (Pico SDK + TinyUSB), выставляет флешку наружу как USB Mass Storage. Программа `usb_token` v0.1, Release от 11.03.2026. Скрытое хранилище `0x10100000` (704 КБ) открывается 4-значным PIN, который вводится физически энкодером. Дамп снят через `picotool save -a backup_full.bin` из BOOTSEL (на RP2040 нет защиты флеша от считывания), образ 2 МБ.

## Карта образа

| Область | Адрес | Что там |
| --- | --- | --- |
| boot2 | `0x10000000` | вторичный загрузчик, 256 б |
| Код | `0x10000100–0x100067f0` | ~26 КБ логики токена |
| Пусто | `0x10010000–0x100fffff` | стёртая флешка `0xFF` |
| Хранилище | `0x10100000–0x101b0000` | 704 КБ, энтропия 8.0 (шифр) |

Точка входа — reset-хендлер `0x100001f6`. Энтропия: DiE на весь файл даёт среднее 3.77 (обман усреднения `0xFF`-провала с шифрованным блоком), но поблочно у хранилища плато 8.0 — это шифр или сжатие, а не открытый текст.

## Принцип работы

Bare-metal суперцикл `main` (`0x1000089c`): `runtime_init` → `board_gpio_init` → `tud_init` → вечный цикл `tud_task_ext` + `app_led_task`. Прикладная логика — в колбэках USB-MSC, не в главном цикле. **PIN гейтит только видимость флешки на хосте, не крипту**. Механизм дотрассирован: `board_gpio_init` (`0x10000ab0`) — блокирующий цикл энкодера, возвращает управление в `main` только после верного PIN; безусловный `tud_init` выполняется уже после него, поэтому без кода USB не поднимается. Успех проверка отмечает флагом `*(uint8_t*)0x20002ED2 = 1`, его читает `app_led_task` (`0x100009a4`) для анимации «разблокировано» (бегущие цифры 0–9 через таблицу сегментов `0x10005508`).

## Карта прикладных функций

| Адрес | Имя | Что делает |
| --- | --- | --- |
| `0x1000089c` | `main` | суперцикл (остался и лейбл `main_hypotesa`) |
| `0x10000ab0` | `board_gpio_init` | GPIO энкодера/LED; входы GPIO 27/28/29 |
| `0x100009a4` | `app_led_task` | индикация цифр PIN, 10 GPIO через SIO `0xd0000014`/`0xd0000018` |
| `0x100002e8` | `tud_msc_inquiry_cb` | SCSI INQUIRY: `POSILABS` / `RP2040 Flash MSC` |
| `0x100008d4` | `tud_descriptor_string_cb` | строки USB (serial `123456`) |
| `0x10000354` | `msc_read10_decrypt_storage` | read10: читает хранилище и расшифровывает сектор |
| `0x1000053c` | `msc_write10_encrypt_storage` | write10: шифрует сектор перед записью во флеш |

Переименования и комментарии закоммичены в общий версионный Ghidra-проект (только метаданные, байты образа не тронуты). Рабочий процесс: файл сначала Check Out (writable), потом Check In. Если файл эксклюзивно выкачан другим участником — он read-only, а `checkin-program` через MCP падает с `unknown consumer`; надо попросить освободить (Undo Checkout или Check In). При работе на заблокированном файле может появиться приватный не-версионный дубль `имя.bin.1` — после успешного check-in он лишний и удаляется. У `0x1000089c` `main_hypotesa` остался primary-лейблом, `main` добавлен вторым.

## Механизм шифрования (главная находка)

Хранилище зашифровано самодельной XOR-гаммой в стиле CTR. Ключ — фиксированные константы прошивки, PIN в вывод гаммы не входит. Для 16-байтного блока при абсолютном LBA `L` и индексе блока `j` (0..31):

```
s = (L*0x38C9CDA0 + 0x9E37A9EA + j*0x41C64E6D) mod 2^32
keystream_byte_i = старший байт (s + C_i), i = 0..15
plaintext = ciphertext XOR keystream
```

Константы `C_i` и параметры — пул `0x100004ec..0x10000538` (read-only XIP-флеш). Полный дешифратор — `attack1/decrypt_storage.py`. Проверка: сектор 0 расшифровывается в `EB 3C 90 "MSDOS5.0"` c сигнатурой `55 AA` — валидный загрузчик FAT12 (`MSDOS5.0` — штатное OEM-имя форматтера, не про ОС).

## Что внутри

Расшифрованный **FAT12**-том (BPB: 512 б/сектор, 1 сектор/кластер, 2048 total sectors, 2 FAT, 512 root, sectors/FAT 6 → 2000 кластеров данных < 4085 = FAT12) → `your_prize.zip` → `readme.txt` + `layers.zip` → матрёшка из 1337 запароленных zip (пароль слоя = его номер, `7z x -p$N layer_$N.zip`) → `prize.html` (rickroll). Финал содержательной нагрузки не несёт, ценность — сам путь вскрытия. Строка `123456` (`0x1000537c`) — USB iSerialNumber, не PIN (таблица дескрипторов `0x10006728`: PositiveLabs / RP2040 Flash MSC / 123456 / Flash Disk).

## PIN (восстановлен)

**PIN = `3952`.** Проверка — внутри блокирующего цикла `board_gpio_init` (`0x10000ab0`), на 4-м нажатии кнопки энкодера: цикл `0x10000c82` (индексы 1..4) сравнивает введённые цифры (`sp+0x34`) с эталоном в rodata **`0x100054FF`** (байты `00 03 09 05 02`, нулевой — dummy → `3 9 5 2`). На каждую совпавшую ведущую цифру — задержка 50 мс (`FUN_1000239c(0x32)`), выход на первом несовпадении: feedback/timing-оракул, на живом устройстве PIN снимается за ≤40 прокруток. Эталон в образе встречается один раз, ссылается на него один указатель (`DAT_10000e10`) — запасного PIN нет. Подтверждено симуляцией проверщика (`pin/pin_sim.py`): полный перебор 10⁴ принимает ровно один код — `3952`. Подробности — [`pin/README.md`](../pin/README.md).

## Векторы атаки (отчёты в репозитории)

- `attack1/` — фиксированный ключ шифрования в прошивке (CWE-321): оффлайн-дешифровка из дампа + PoC `decrypt_storage.py`
- `attack2/` — подмена содержимого / evil-maid (CWE-345): той же известной гаммой шифруется вредонос и пишется в флеш. PoC: `forge_sector.py` (ковка одного сектора) и `evil_maid.py` (сессия 3 — подмена приза целиком, end-to-end зелёный ~57с). evil_maid: recover гаммы (движок attack3) → decrypt том → развернуть матрёшку `your_prize.zip`→`layers.zip`→1337 AES-слоёв (`layer_N.zip`, пароль=N, извлекает 7z) → финальный `prize.html` НЕ заменяется, а инъецируется decompression-бомбой (`bomb_html.py`: малый gzip-сид base64 → async-разжатие в память → OOM вкладки; молчит, не трогает DOM → внешне неотличим от rickroll-оригинала) → свернуть теми же паролями → re-encrypt → forged storage/dump. Слои остаются подлинными на вид (пароль=номер сохранён). `matryoshka.py` (unwrap/rewrap) переиспользуема. Зависимости: mtools (FAT12) + 7z (AES-256). Тесты: `test_matryoshka.py` (4, с фальсификацией пароль=номер), `test_bomb_html.py` (5). ВАЖНО честная граница: site-isolation → гибнет вкладка, не система; overlap-бомбу Fifield запаролить нельзя (шифрование ломает overlap), поэтому пароль на слое-обёртке, бомба внутри незашифрована
- `attack3/` — **самодельный шифр вскрывается из одного холодного дампа** (CWE-327/321/323; влит бывший `attack7`, старый `attack3` про слабость шифра стал вводным разделом): гамма — старший байт линейной функции позиции, где `B=0x41C64E6D` (множитель glibc `rand()`), `W=0x9E3779B1` (golden-hash Кнута), `A=32*B mod 2^32` (производный, генератор непрерывен, 32 блока/сектор), `C_i=(i-1)*W`. Единственный секрет — `seed` — восстанавливается интервальным пересечением по known-plaintext FAT12 + нулевым reserved-секторам (in-band оракул) и отбирается по CRC вложенного ZIP. Мини-PoC принципа — `known_plaintext.py` (XOR предсказуемых байтов → гамма); полное восстановление — `recover_keystream.py` (том за 0.5с без прошивки/PIN/устройства), тесты `test_recover.py` (с фальсификацией) зелёные. Доп-векторы (`extra_attacks.py`): N1 in-band оракул, N3 мастер-таблица гаммы (ключ всей серии), N4 two-time-pad, N5 нет secure-erase. NB: `seed` восстанавливается КЛАССОМ ~844 значений, все дают побайтово идентичную расшифровку (истинный `0x9E37A9EA`), различить из дампа нельзя и не нужно
- `attack4/` — **физический перебор PIN** (CWE-307 + тайминг-оракул CWE-208): нет ни блокировки после неверных попыток, ни задержки эскалации, а проверщик по 50 мс задерживается на каждую верную ведущую цифру → PIN снимается посимвольно за ≤40 инъекций. PoC-стенд — эмулятор энкодера на Pico (`attack4/pico-encoder-emulator/`, PlatformIO + arduino-pico, собирается ~38 КБ, коммит `b449e7c`): open-drain подменяет линии энкодера (GPIO 29=A, 27=B, 28=SW, активный ноль) и перебирает 0000–9999 с регулируемой скоростью; jog-режим для калибровки квант-шагов на цифру. Детали текущей прошивки (режимы свипа, скорость, грабли сборки/запуска) — в секции «Attack4» ниже. **Отчёт `attack4/README.md` написан** (сессия 2). ВАЖНАЯ ПОПРАВКА к секциям ниже: текущий `main.cpp` (rewrite, коммит `c27d016`) — это ручные примитивы (`turnOne`/`pressButton`/`gotoDigit`, ввод `n<pin>`/`k`, jog, `senseMonitor`); **авто-sweep `0000–9999` и оракульный режим `o` из него ВЫРЕЗАНЫ** при переписывании (были в ранних коммитах) — их надо вернуть. Логику атаки (ручной ввод + оракул ≤40, зависимость от калибровки `QUARTERS_PER_STEP`/`INVERT_DIR`/reset-on-confirm) валидирует со-симулятор `attack4/sim/emulator_sim.py` без железа; на живом сейфе не прогонялось
- `attack5/` — **оракул гаммы из «пустого места» диска** (CWE-805): MSC объявляет 2048 секторов (1 МиБ, `param_2 < 0x800` в `0x10000354`), а шифрованная область — 704 КиБ; стёртый флеш за её концом «расшифровывается» и отдаётся хосту как `~гамма`. Проверено по дампу: с LBA 1403 граница, 644 сектора ≈ 322 КиБ чистой гаммы одним чтением (PoC `keystream_leak_demo.py`; исключение — LBA 2047 с зашифрованными нулями). Шаг восстановления генератора реализован (сессия 3): `keystream_leak_demo.py` секция [4] импортирует движок из `attack3/recover_keystream.py` и по собранной гамме (ks = 0xFF ^ served) решает (A, seed, B, W) без вшитых констант, затем расшифровывает хранилище до валидного по CRC ZIP — end-to-end зелёный. NB: seed выходит тем же КЛАССОМ эквивалентности, что в attack3 (0x9E37A9B7), точечный не восстановим — старший байт >>24 скрывает младшие 24 бита независимо от L; на побайтовой точности не сказывается. Подача пересмотрена (по замечанию: вектор смотрелся как "ещё один способ достать гамму"): теперь это оракул расшифровки за границей области MSC — живое устройство само декодирует и отдаёт за концом хранилища; честно, что выигрыш над attack3 = только AV:L (без дампа/выпайки/реверса), плюс контрфактик (баг границ утёк бы keystream и при ключе из PIN, масштаб падал бы до одного устройства) и обобщение класса CWE-805. ВАЖНО: read10 читает ФЛЕШ-хранилище, не RAM; ключа-в-RAM в прошивке нет (в RAM только флаг 0x20002ED2) — версия "ключ в RAM, найти по слепку" механически неверна для этого бага. CVSS 4.6 (AV:P) → ~6.1 (AV:L, хост уже видит диск). Починка: объявлять в MSC `0x580` секторов / за хвостом отвечать ошибкой. Тот же корень закрывает гипотезу 6 (переполнение LBA) — прямой `param_2 < 0x800` режет её до всякой арифметики переноса
- `attack6/` — **подмена прошивки через BOOTSEL** (CWE-494): подписи нет, bootrom ждёт только CRC32 boot2, а BOOTSEL-режим — штатный drag-and-drop всей флешки за ~30 секунд физического доступа. Собраны и верифицированы дизассемблером 2 импланта из чистого образа: `evil_anypin` (2 байта: `bne fail`→`nop` на `0x10000c8c` — разблокировка любой комбинацией) и `evil_pin1234` (4 байта: эталон `0x100054FF` 3952→1234); оба упакованы в UF2 (`evil_*.uf2`, family `0xE48BFF56`) для drag-and-drop. Стелс-вариант «двойного PIN» упёрся в отсутствие кодовой пещеры в ±254 байта ветки — TODO. Детект — хэш образа через `picotool save -a`; фикс — RP2350 secure boot. Через USB-MSC прошивка недостижима (границы attack5), доставка только физическая
- Побочная находка (CWE-613, low, отчёта нет): разблокировка «липкая» — нет auto-lock, таймаута и повторной блокировки, сейф открыт по USB до снятия питания; энкодер после верного PIN не опрашивается (гейт одноразовый — `board_gpio_init` вернул управление в `main`, дальше суперцикл). Перед оформлением подтвердить по Ghidra, что суперцикл энкодер действительно не перечитывает

Ориентиры CVSS: вектор 1 — 4.6→6.1, вектор 2 — 6.1→7.8, вектор 3 — 4.6→6.1. Аппаратной защиты на RP2040 нет — ни secure boot, ни readout protection, ни OTP под ключи (появились только в RP2350). Из четырёх исходных гипотез подтвердилась «ключ не зависит от кода»; перебор без блокировки, небезопасное сравнение и переполнение буфера для доступа к данным не нужны.

## Сессия 2 — прочие итоги и поправки

- **`FUN_1000239c` = `sleep_ms(ms)`** (Pico SDK: `make_timeout_time_ms` + WFE/alarm по 64-бит таймеру, GPIO не трогает). Размечено в Ghidra: имя `sleep_ms` на `0x1000239c`, plate-коммент, pre-коммент CWE-208 на call-site `0x10000c92`. Check-in через MCP падает (`unknown consumer`) — правки в открытой сессии, коммит в VCS вручную через GUI
- **boot2 CRC — норма, НЕ аномалия**: сохранённый `0x7A4EB274` = CRC-32/MPEG-2 над первыми `0xFC` байтами (штатный алгоритм Pico SDK); прежнее «расхождение» — от рефлектнутого zlib crc32 (`0xD4A3FD6A`). boot2 не подменён
- **До верного PIN USB неактивен**: `main` зовёт `board_gpio_init()` затем `tud_init(0,0)` (call-site `0x100008a6`); цикл `board_gpio_init` — бесконечный, единственный выход при `{3,9,5,2}`, чистой энкодерной лазейки нет. Атак по USB-протоколу без PIN нет; «без PIN» через USB — только BOOTSEL/PICOBOOT или VBUS-глитч
- **Поправка к SWD-вектору**: запись флага `0x20002ED2=1` НЕ поднимает USB (флаг — только LED-анимация в `app_led_task`); настоящий гейт — возврат из `board_gpio_init`. SWD-разблокировка = форсировать PC мимо цикла
- **V14 (warm-reset флага) — нужен 1 HW-замер**: статикой bss-zero, покрывающий `0x20002ED2`, не найден; SRAM при тёплом ресете не чистится → возможен обход, но решается только измерением SWD до/после reset
- **TinyUSB MSC (V3) — публичных CVE нет** (ни GHSA, ни задокументированных OSS-Fuzz крашей по MSC); версию из release-сборки не зафиксировать. Поверхность фаззинга есть, дыры нет — не переоценивать
- **rp2040js — РАБОЧИЙ эмуляторный стенд** `attack4/emulator-stand/`: с реальным bootrom (качается `fetch-bootrom.sh`, BSD-3, не вендорится) прошивка грузится целиком, крутится в цикле энкодера (USB закрыт до PIN — подтверждает F1/F2 на живом образе), а инжекция импульсов на GPIO 27/28/29 + closed-loop-набор открывает сейф вводом `3952` (флаг `0x20002ED2=1`), `3951` — нет. Калибровка энкодера снята в эмуляторе: 30 мс/фронт — чистый монотонный счёт (быстрее — теряет фронты как дребезг). Ключ к прогону: `mcu.step()` НЕ двигает часы, нужно повторять цикл `Simulator.execute()` (tick по циклам + перемотка через `core.waiting`/WFE). USB device-mode без MSC-хоста → стенд доводит до факта разблокировки, не до монтирования; тайминг-оракул как алгоритм — в `attack4/sim/`. Медленно (~5 с виртуальных ≈ 100 с реальных)
- Новые/уточнённые векторы — в `vectors/NEW_VECTORS.md` секция «Сессия 2» (V26 полный клон устройства, V27 домашний глитчер, разрешения V22/V3/V8/V14)

## Attack4 — эмулятор энкодера (прошивка Pico)

`attack4/pico-encoder-emulator/` — прошивка для второго RP2040 (Raspberry Pi Pico), который выдаёт себя за поворотный энкодер + кнопку сейфа и физически перебирает PIN. Управление — однобуквенными командами по USB-serial (115200). Собирается PlatformIO: `pio run` / `pio run -t upload` (arduino-pico earlephilhower core через форк платформы maxgerhardt).

Подключение (только 3 сигнала + земля, open-drain, тянем только в LOW): Pico `GP2→A` (target GPIO29), `GP3→B` (GPIO27), `GP4→SW` (GPIO28), `GND↔GND`; `GP5` — опциональный вход SENSE (индикатор разблокировки). 3V3/VBUS **не** соединять.

Команды и текущие настройки (в `src/main.cpp`):
- Скорость — константа `SWEEP_SPEED_PCT` (сейчас **100%**, потолок `SPEED_MAX_PCT=1000`, рантайм `+`/`-`). Пробовали 400% с урезанными таймингами под «нет дребезга» — на живой мишени **терялись фронты/промахи**, вернули исходные консервативные тайминги (`edge=3000…attemptgap=150000` мкс).
- Перебор по умолчанию — **окрестность ±`SWEEP_RADIUS`(=50) вокруг `SWEEP_CENTER`(=3952)**, т.е. окно `3902..4002` (находит верный PIN за ~55 с). Клавиша **`f`** переключает на полный `0000..9999` (и обратно). `r` — сброс в начало текущего окна, `j<n>` — прыжок на попытку, `g`/`s` — старт/пауза.
- **`k`** — разовый надёжный ввод известного PIN 3952 (`KNOWN_PIN`) от чистого старта.
- SENSE по умолчанию **выключен** (`SENSE_ENABLE=false`) — эмулятор вводит код «вслепую» и не подтверждает разблокировку электрически; сейф при верном PIN откроется независимо. Для авто-подтверждения — подключить индикатор на GP5 и включить SENSE + верный `SENSE_ACTIVE_LEVEL`.
- Атака зависит от калибровки счёта шагов (`QUARTERS_PER_STEP`, `INVERT_DIR`, `INITIAL_VALUE`, `RESET_AFTER_*`) — перед боевым свипом проверять jog-режимом (`u`/`d`/`z`), что дисплей мишени считает 1-в-1.

Грабли окружения/сборки:
- Первый `pio run` тянет arduino-pico core рекурсивным клоном (pico-sdk + btstack/tinyusb/mbedtls с тест-данными) — нужно **несколько ГБ** свободного места, иначе падает `No space left on device` на середине клона.
- Порт **переезжает** `/dev/ttyACMx` при каждом переподключении платы — цепляться по стабильному пути `/dev/serial/by-id/usb-Raspberry_Pi_Pico_*` (serial платы `50443405B0780B1C`).
- Баннер печатается **один раз в `setup()`**; arduino-pico при переоткрытии монитора плату не ресетит → при подключении баннера не будет, но команды (`?`,`h`,…) отвечают. Через `pyserial` консоль «молчит», если **не поднять DTR** (`s.dtr=True` при открытии); `pio device monitor`/`screen` поднимают DTR сами.

## Attack4 — оракульный режим (тайминг-атака ≤40 прокруток)

Дописан в ту же прошивку `attack4/pico-encoder-emulator/src/main.cpp` (не тронут dumb-sweep). Механизм оракула вытащен из декомпиляции `reversing/program_decompiled.c` (Ghidra на ноуте не нужна):

- Проверка PIN на 4-м нажатии (`FUN_10000ab0`, блок с `2 < uVar18`): побайтовое сравнение с эталоном, на **каждую совпавшую ведущую цифру** — `FUN_1000239c(0x32)` = `sleep_ms(50)`. `FUN_1000239c` — обычный `sleep_ms` (busy-wait/WFE по таймеру, **GPIO не трогает**; зовётся ещё с `2` для тика опроса и `200` для кадров анимации). Внутри цикла сравнения ни один GPIO не переключается → все выходы заморожены ровно `50 мс × k`, где `k` — длина совпавшего префикса (0..4). Совпало 4 → `_DAT_d0000014 = 0x400` (SET GPIO10) + `*0x20002ED2 = 1` (unlock); иначе — анимация отказа 3× мигание GPIO10 по 200 мс ≈ 1.2 с, сброс буфера, ввод заново (fail перезапускает ввод в том же блокирующем цикле — подтверждено пользователем на железе)
- Раскладка индикаторных GPIO мишени (таблицы из бинаря по `DAT_10000df0`/`DAT_10000df4`): **GPIO 0–9** — сегменты цифры, таблица цифра→пин `[7,6,5,4,3,2,1,0,9,8]` (горит один); **GPIO 10–13** — позиция/прогресс, таблица `[13,12,11,10]` (GPIO13 на 1-й вводимой цифре … GPIO10 на 4-й); **GPIO 27/28/29** — входы энкодера B/SW/A. **GPIO10 (`0x400`)** несёт всё нужное для оракула: мигает как позиция 4 вокруг момента замера, мигает в анимации отказа, латчится в SET при разблокировке — лучший пин для SENSE
- Подключение SENSE: **Pico GP5 (физический вывод 7) → линия GPIO10 сейфа** (пятак токоограничивающего резистора со стороны чипа, чистые 3.3 В), земля уже общая с энкодерной частью; 3V3/VBUS между платами не соединять
- Замер: после отпускания 4-й кнопки прошивка семплит SENSE и берёт длину самого длинного «замороженного» интервала, начинающегося в первые ~15 мс → `k = round((freeze − base)/step)`. Робастно к периоду мигания в покое, не зависит от «первого фронта»
- Алгоритм атаки (`oracleAttack`): для позиции 0..3 гонять цифру 0..9 с известным префиксом, мерить `k`; верная цифра — единственная с `k ≥ pos+1`, ранний выход при находке (в среднем ~22 ввода, худший 40). В конце ввести найденный PIN и подтвердить unlock по SENSE
- Команды консоли (115200): `e` toggle SENSE, `o` запуск атаки (`s` прерывает), `m<sec>` монитор переходов SENSE (поиск пятака: тыкать грабером по GPIO 10–13/0–9, искать `edges>0`), `t<code>` разовый замер think-time (калибровка; `t3952`→k=4, `t0000`→k=0), `B<ms>` set base, `S<ms>` set step. Параметры по умолчанию: `ORACLE_STEP_MS=50`, `ORACLE_BASE_MS=0`, guard 15 мс, окно 700 мс. Калибровка: `base ≈ freeze(k=0)`, `step ≈ (freeze(k=4)−base)/4` (ожидаем ~50)
- Статус: **ОТРАБОТАНО НА ЖИВОМ СЕЙФЕ (сессия 3)** — оракул восстановил PIN за 23 попытки вслепую. Детали, калибровки и видео — в секции «Attack4 — живое железо (сессия 3)» ниже и в `attack4/README.md`
- TODO Ghidra (на ПК, где есть Ghidra+MCP): `FUN_1000239c` → `sleep_ms`, а на call-site `0x10000c92` (вызов с `0x32` в цикле сравнения PIN) — комментарий `timing oracle: 50 ms per matching PIN digit -> CWE-208`. Пользователь предлагал имя `stupid_50_ms_delay` на самой функции; точнее развести (имя = суть функции `sleep_ms`, «глупость» = комментарий на месте вызова), окончательный выбор — на ПК

Диагностика окружения ноута: атакующая Pico `2e8a:000a` serial `50443405B0780B1C`, `/dev/ttyACM0`, стабильный путь `/dev/serial/by-id/usb-Raspberry_Pi_Pico_50443405B0780B1C-if00`. На ноуте `pyserial` нет — консоль дёргается через `nix-shell -p python3Packages.pyserial` с `dtr=True`. Симптом «плата не видна» был из-за **charge-only/битого кабеля** (`error -71` в журнале ядра, устройство на шине есть, но не энумерируется) — смена кабеля лечит.

## Attack4 — живое железо (сессия 3)

Физический оракул отработан на настоящем сейфе: PIN `3952` восстановлен за **23 попытки** вслепую (предел ≤40). Атакующий контроллер — **RP2040-Zero** (пады подписаны по GP, распиновка кода не менялась: `GP2`→GPIO27 B, `GP3`→GPIO28 SW, `GP4`→GPIO29 A, `GP5`→GPIO10 SENSE, GND). Видео с таймером — `attack4/oracle-attack.mp4`.

Тайминг-оракул читается по **GPIO10**: после 4-го нажатия выходы заморожены `50 мс × k`, замер длины фриза даёт чистую лесенку `0/52/102/152/202 мс` (k=0..4, k=4 = UNLOCK). `k` классифицируется строго по длине фриза, разблокировка при `k ≥ 4` (и отказ, и разблокировка после фриза гонят GPIO10 в HIGH, поэтому «high в конце» ≠ разблокировка — различает только длина).

Калибровки (в дефолтах `main.cpp`), дались тяжело — каждая закрыла конкретный симптом:

- **резисторы 150–330 Ом последовательно на A (`GP4`) и B (`GP2`)** гасят звон/задвоение фронтов на живых линиях
- **в покое линии в `INPUT_PULLUP`** (не `INPUT`): подтяжка контроллера параллельно слабой внутренней подтяжке сейфа убирает нарастающую со временем наводку («чем дольше подключён — тем сильнее дребезг»)
- детент — **пачка 4 фронтов по 5 мс через `delayMicroseconds`**; `noInterrupts` вокруг пачки вешал USB-CDC — убран, `delayMicroseconds` ждёт до отметки таймера и сам не джиттерит
- **пауза 100 мс между детентами** > 80-мс окна группировки сейфа (`DAT_100010fc`), иначе детенты сливаются/дробятся при авто-наборе
- **4-е нажатие синхронизируется с низкой фазой мигания GPIO10** (это индикатор позиции 4, мигает 300 мс), чтобы фриз читался как низкий интервал

Тайминговые окна декодера энкодера вытащены из образа (`program.bin`, таймер в µs): `DAT_100010f8=30 мс` (приём фронта), `DAT_100010fc=80 мс` (группировка детента), `DAT_100010f0/e08=300 мс` (мигание/тайм-аут). Подтверждены из образа: флаг разблокировки `0x20002ED2`, таблицы сегментов `[7,6,5,4,3,2,1,0,9,8]` и позиций `[13,12,11,10]`, эталон PIN по `DAT_10000e10=0x100054ff`.

**Разблокировка живёт в SRAM и переживает короткий сброс** (подтверждает V14): флаг `0x20002ED2` не чистится быстрым передёргиванием, сейф поднимается уже открытым — перед каждым прогоном нужен **полный обесток 5–10 с**. Отдельный баг сам по себе (unlock переживает reset).

Прошивка/окружение: `pio run -t upload` на этом ноуте (NixOS) ненадёжен — авто-детект хватает `/dev/ttyS0`, а его picotool-поток ждёт авто-монтирование RPI-RP2, которого на NixOS нет (+ `pio` в bwrap). Надёжная заливка — **`picotool load -x <uf2>`** после 1200-touch (`pyserial dtr=False`) или ручного BOOTSEL; `platformio.ini` прибит `upload_port = /dev/ttyACM*` (фикс ttyS0). udev-варнинг `pio` — ложный (правила из `~/huix/nixos/services/utils/embedded.nix` активны, доступ есть; ругается bwrap-обёртка). `-f` у picotool не работает — прошивка не выставляет reset-интерфейс.
