Трек Positive Technologies на ЛЦТ 2026 — получить доступ к прошивке кибер-сейфа и описать уязвимости. Эта память общая для команды, лежит в репозитории; приватное и личное сюда не пишем.

## Устройство

Кибер-сейф на **Raspberry Pi RP2040** (двухъядерный Cortex-M0+, в Ghidra `ARM:LE:32:Cortex`, база XIP `0x10000000`), bare-metal (Pico SDK + TinyUSB), выставляет флешку наружу как USB Mass Storage. Программа `usb_token` v0.1, Release от 11.03.2026. Скрытое хранилище `0x10100000` (704 КБ) открывается 4-значным PIN, который вводится физически энкодером. Дамп снят через `picotool save -a backup_full.bin` из BOOTSEL (на RP2040 нет защиты флеша от считывания), образ 2 МБ.

## Карта образа

| Область | Адрес | Что там |
| --- | --- | --- |
| boot2 | `0x10000000` | вторичный загрузчик, 256 б |
| Код | `0x10000100–0x100067f0` | ~26 КБ логики токена |
| Пусто | `0x10010000–0x100fffff` | стёртая флешка `0xFF` |
| Хранилище | `0x10100000–0x101b0000` | 704 КБ, энтропия 8.0 (шифр) |

Точка входа — reset-хендлер `0x100001f6`. Энтропия: DiE на весь файл даёт среднее 3.77 (обман усреднения `0xFF`-провала с шифрованным блоком), но поблочно у хранилища плато 8.0 — это шифр или сжатие, а не открытый текст.

## Принцип работы

Bare-metal суперцикл `main` (`0x1000089c`): `runtime_init` → `board_gpio_init` → `tud_init` → вечный цикл `tud_task_ext` + `app_led_task`. Прикладная логика — в колбэках USB-MSC, не в главном цикле. **PIN гейтит только видимость флешки на хосте, не крипту**. Механизм дотрассирован: `board_gpio_init` (`0x10000ab0`) — блокирующий цикл энкодера, возвращает управление в `main` только после верного PIN; безусловный `tud_init` выполняется уже после него, поэтому без кода USB не поднимается. Успех проверка отмечает флагом `*(uint8_t*)0x20002ED2 = 1`, его читает `app_led_task` (`0x100009a4`) для анимации «разблокировано» (бегущие цифры 0–9 через таблицу сегментов `0x10005508`).

## Карта прикладных функций

| Адрес | Имя | Что делает |
| --- | --- | --- |
| `0x1000089c` | `main` | суперцикл (остался и лейбл `main_hypotesa`) |
| `0x10000ab0` | `board_gpio_init` | GPIO энкодера/LED; входы GPIO 27/28/29 |
| `0x100009a4` | `app_led_task` | индикация цифр PIN, 10 GPIO через SIO `0xd0000014`/`0xd0000018` |
| `0x100002e8` | `tud_msc_inquiry_cb` | SCSI INQUIRY: `POSILABS` / `RP2040 Flash MSC` |
| `0x100008d4` | `tud_descriptor_string_cb` | строки USB (serial `123456`) |
| `0x10000354` | `msc_read10_decrypt_storage` | read10: читает хранилище и расшифровывает сектор |
| `0x1000053c` | `msc_write10_encrypt_storage` | write10: шифрует сектор перед записью во флеш |

Переименования и комментарии закоммичены в общий версионный Ghidra-проект (только метаданные, байты образа не тронуты). Рабочий процесс: файл сначала Check Out (writable), потом Check In. Если файл эксклюзивно выкачан другим участником — он read-only, а `checkin-program` через MCP падает с `unknown consumer`; надо попросить освободить (Undo Checkout или Check In). При работе на заблокированном файле может появиться приватный не-версионный дубль `имя.bin.1` — после успешного check-in он лишний и удаляется. У `0x1000089c` `main_hypotesa` остался primary-лейблом, `main` добавлен вторым.

## Механизм шифрования (главная находка)

Хранилище зашифровано самодельной XOR-гаммой в стиле CTR. Ключ — фиксированные константы прошивки, PIN в вывод гаммы не входит. Для 16-байтного блока при абсолютном LBA `L` и индексе блока `j` (0..31):

```
s = (L*0x38C9CDA0 + 0x9E37A9EA + j*0x41C64E6D) mod 2^32
keystream_byte_i = старший байт (s + C_i), i = 0..15
plaintext = ciphertext XOR keystream
```

Константы `C_i` и параметры — пул `0x100004ec..0x10000538` (read-only XIP-флеш). Полный дешифратор — `attack1/decrypt_storage.py`. Проверка: сектор 0 расшифровывается в `EB 3C 90 "MSDOS5.0"` c сигнатурой `55 AA` — валидный загрузчик FAT12 (`MSDOS5.0` — штатное OEM-имя форматтера, не про ОС).

## Что внутри

Расшифрованный **FAT12**-том (BPB: 512 б/сектор, 1 сектор/кластер, 2048 total sectors, 2 FAT, 512 root, sectors/FAT 6 → 2000 кластеров данных < 4085 = FAT12) → `your_prize.zip` → `readme.txt` + `layers.zip` → матрёшка из 1337 запароленных zip (пароль слоя = его номер, `7z x -p$N layer_$N.zip`) → `prize.html` (rickroll). Финал содержательной нагрузки не несёт, ценность — сам путь вскрытия. Строка `123456` (`0x1000537c`) — USB iSerialNumber, не PIN (таблица дескрипторов `0x10006728`: PositiveLabs / RP2040 Flash MSC / 123456 / Flash Disk).

## PIN (восстановлен)

**PIN = `3952`.** Проверка — внутри блокирующего цикла `board_gpio_init` (`0x10000ab0`), на 4-м нажатии кнопки энкодера: цикл `0x10000c82` (индексы 1..4) сравнивает введённые цифры (`sp+0x34`) с эталоном в rodata **`0x100054FF`** (байты `00 03 09 05 02`, нулевой — dummy → `3 9 5 2`). На каждую совпавшую ведущую цифру — задержка 50 мс (`FUN_1000239c(0x32)`), выход на первом несовпадении: feedback/timing-оракул, на живом устройстве PIN снимается за ≤40 прокруток. Эталон в образе встречается один раз, ссылается на него один указатель (`DAT_10000e10`) — запасного PIN нет. Подтверждено симуляцией проверщика (`pin/pin_sim.py`): полный перебор 10⁴ принимает ровно один код — `3952`. Подробности — [`pin/README.md`](../pin/README.md).

## Векторы атаки (отчёты в репозитории)

- `attack1/` — фиксированный ключ шифрования в прошивке (CWE-321): оффлайн-дешифровка из дампа + PoC `decrypt_storage.py`
- `attack2/` — подмена содержимого / evil-maid (CWE-345): той же известной гаммой шифруется вредонос и пишется в флеш
- `attack3/` — слабость самого шифра (CWE-327): линейная гамма вскрывается known-plaintext
- `attack4/` — **физический перебор PIN** (CWE-307 + тайминг-оракул CWE-208): нет ни блокировки после неверных попыток, ни задержки эскалации, а проверщик по 50 мс задерживается на каждую верную ведущую цифру → PIN снимается посимвольно за ≤40 инъекций. PoC-стенд — эмулятор энкодера на Pico (`attack4/pico-encoder-emulator/`, PlatformIO + arduino-pico, собирается ~38 КБ, коммит `b449e7c`): open-drain подменяет линии энкодера (GPIO 29=A, 27=B, 28=SW, активный ноль) и перебирает 0000–9999 с регулируемой скоростью; jog-режим для калибровки квант-шагов на цифру. ## Attack4 — эмулятор энкодера (прошивка Pico)

`attack4/pico-encoder-emulator/` — прошивка для второго RP2040 (Raspberry Pi Pico), который выдаёт себя за поворотный энкодер + кнопку сейфа и физически перебирает PIN. Управление — однобуквенными командами по USB-serial (115200). Собирается PlatformIO: `pio run` / `pio run -t upload` (arduino-pico earlephilhower core через форк платформы maxgerhardt).

Подключение (только 3 сигнала + земля, open-drain, тянем только в LOW): Pico `GP2→A` (target GPIO29), `GP3→B` (GPIO27), `GP4→SW` (GPIO28), `GND↔GND`; `GP5` — опциональный вход SENSE (индикатор разблокировки). 3V3/VBUS **не** соединять.

Команды и текущие настройки (в `src/main.cpp`):
- Скорость — константа `SWEEP_SPEED_PCT` (сейчас **100%**, потолок `SPEED_MAX_PCT=1000`, рантайм `+`/`-`). Пробовали 400% с урезанными таймингами под «нет дребезга» — на живой мишени **терялись фронты/промахи**, вернули исходные консервативные тайминги (`edge=3000…attemptgap=150000` мкс).
- Перебор по умолчанию — **окрестность ±`SWEEP_RADIUS`(=50) вокруг `SWEEP_CENTER`(=3952)**, т.е. окно `3902..4002` (находит верный PIN за ~55 с). Клавиша **`f`** переключает на полный `0000..9999` (и обратно). `r` — сброс в начало текущего окна, `j<n>` — прыжок на попытку, `g`/`s` — старт/пауза.
- **`k`** — разовый надёжный ввод известного PIN 3952 (`KNOWN_PIN`) от чистого старта.
- SENSE по умолчанию **выключен** (`SENSE_ENABLE=false`) — эмулятор вводит код «вслепую» и не подтверждает разблокировку электрически; сейф при верном PIN откроется независимо. Для авто-подтверждения — подключить индикатор на GP5 и включить SENSE + верный `SENSE_ACTIVE_LEVEL`.
- Атака зависит от калибровки счёта шагов (`QUARTERS_PER_STEP`, `INVERT_DIR`, `INITIAL_VALUE`, `RESET_AFTER_*`) — перед боевым свипом проверять jog-режимом (`u`/`d`/`z`), что дисплей мишени считает 1-в-1.

Грабли окружения/сборки:
- Первый `pio run` тянет arduino-pico core рекурсивным клоном (pico-sdk + btstack/tinyusb/mbedtls с тест-данными) — нужно **несколько ГБ** свободного места, иначе падает `No space left on device` на середине клона.
- Порт **переезжает** `/dev/ttyACMx` при каждом переподключении платы — цепляться по стабильному пути `/dev/serial/by-id/usb-Raspberry_Pi_Pico_*` (serial платы `50443405B0780B1C`).
- Баннер печатается **один раз в `setup()`**; arduino-pico при переоткрытии монитора плату не ресетит → при подключении баннера не будет, но команды (`?`,`h`,…) отвечают. Через `pyserial` консоль «молчит», если **не поднять DTR** (`s.dtr=True` при открытии); `pio device monitor`/`screen` поднимают DTR сами.
