Трек Positive Technologies на ЛЦТ 2026 — получить доступ к прошивке кибер-сейфа и описать уязвимости. Эта память общая для команды, лежит в репозитории; приватное и личное сюда не пишем.

## Устройство

Кибер-сейф на **Raspberry Pi RP2040** (двухъядерный Cortex-M0+, в Ghidra `ARM:LE:32:Cortex`, база XIP `0x10000000`), bare-metal (Pico SDK + TinyUSB), выставляет флешку наружу как USB Mass Storage. Программа `usb_token`; скрытое хранилище начинается по адресу `0x10100000` и занимает 704 КиБ. Четырёхзначный PIN вводится энкодером и задерживает запуск USB, но не участвует в выводе гаммы. Сохранённый полный дамп флеш-памяти — 2 МиБ

## Карта образа

| Область | Адрес | Что там |
| --- | --- | --- |
| boot2 | `0x10000000` | вторичный загрузчик, 256 б |
| Код | `0x10000100–0x100067f0` | ~26 КБ логики токена |
| Пусто | `0x10010000–0x100fffff` | стёртая флешка `0xFF` |
| Хранилище | `0x10100000–0x101affff` | 704 КиБ, шифрованные данные и стёртый хвост |

Точка входа — reset-хендлер `0x100001f6`. Энтропия: DiE на весь файл даёт среднее 3.77 (обман усреднения `0xFF`-провала с шифрованным блоком), но поблочно у хранилища плато 8.0 — это шифр или сжатие, а не открытый текст.

## Принцип работы

Bare-metal суперцикл `main` (`0x1000089c`): `runtime_init` → `board_gpio_init` → `tud_init` → вечный цикл `tud_task_ext` + `app_led_task`. Прикладная логика — в колбэках USB-MSC, не в главном цикле. **PIN гейтит только видимость флешки на хосте, не крипту**. Механизм дотрассирован: `board_gpio_init` (`0x10000ab0`) — блокирующий цикл энкодера, возвращает управление в `main` только после верного PIN; безусловный `tud_init` выполняется уже после него, поэтому без кода USB не поднимается. Успех проверка отмечает флагом `*(uint8_t*)0x20002ED2 = 1`, его читает `app_led_task` (`0x100009a4`) для анимации «разблокировано» (бегущие цифры 0–9 через таблицу сегментов `0x10005508`).

## Карта прикладных функций

| Адрес | Имя | Что делает |
| --- | --- | --- |
| `0x1000089c` | `main` | суперцикл (остался и лейбл `main_hypotesa`) |
| `0x10000ab0` | `board_gpio_init` | GPIO энкодера/LED; входы GPIO 27/28/29 |
| `0x100009a4` | `app_led_task` | индикация цифр PIN, 10 GPIO через SIO `0xd0000014`/`0xd0000018` |
| `0x100002e8` | `tud_msc_inquiry_cb` | SCSI INQUIRY: `POSILABS` / `RP2040 Flash MSC` |
| `0x100008d4` | `tud_descriptor_string_cb` | строки USB (serial `123456`) |
| `0x10000354` | `msc_read10_decrypt_storage` | read10: читает хранилище и расшифровывает сектор |
| `0x1000053c` | `msc_write10_encrypt_storage` | write10: шифрует сектор перед записью во флеш |

Переименования и комментарии закоммичены в общий версионный Ghidra-проект (только метаданные, байты образа не тронуты). Рабочий процесс: файл сначала Check Out (writable), потом Check In. Если файл эксклюзивно выкачан другим участником — он read-only, а `checkin-program` через MCP падает с `unknown consumer`; надо попросить освободить (Undo Checkout или Check In). При работе на заблокированном файле может появиться приватный не-версионный дубль `имя.bin.1` — после успешного check-in он лишний и удаляется. У `0x1000089c` `main_hypotesa` остался primary-лейблом, `main` добавлен вторым.

## Механизм шифрования (главная находка)

Хранилище зашифровано самодельной XOR-гаммой в стиле CTR. Ключ — фиксированные константы прошивки, PIN в вывод гаммы не входит. Для 16-байтного блока при абсолютном LBA `L` и индексе блока `j` (0..31):

```
s = (L*0x38C9CDA0 + 0x9E37A9EA + j*0x41C64E6D) mod 2^32
keystream_byte_i = старший байт (s + C_i), i = 0..15
plaintext = ciphertext XOR keystream
```

Константы `C_i` и параметры — пул `0x100004ec..0x10000538` (read-only XIP-флеш). Полный дешифратор — `attack1/src/decrypt_storage.py`. Проверка: сектор 0 расшифровывается в `EB 3C 90 "MSDOS5.0"` c сигнатурой `55 AA` — валидный загрузчик FAT12 (`MSDOS5.0` — штатное OEM-имя форматтера, не про ОС).

## Что внутри

Расшифрованный **FAT12**-том (BPB: 512 б/сектор, 1 сектор/кластер, 2048 total sectors, 2 FAT, 512 root, sectors/FAT 6 → 2000 кластеров данных < 4085 = FAT12) → `your_prize.zip` → `readme.txt` + `layers.zip` → матрёшка из 1337 запароленных zip (пароль слоя = его номер, `7z x -p$N layer_$N.zip`) → `prize.html` (rickroll). Финал содержательной нагрузки не несёт, ценность — сам путь вскрытия. Строка `123456` (`0x1000537c`) — USB iSerialNumber, не PIN (таблица дескрипторов `0x10006728`: PositiveLabs / RP2040 Flash MSC / 123456 / Flash Disk).

## PIN (восстановлен)

**PIN = `3952`.** Проверка — внутри блокирующего цикла `board_gpio_init` (`0x10000ab0`), на 4-м нажатии кнопки энкодера: цикл `0x10000c82` (индексы 1..4) сравнивает введённые цифры (`sp+0x34`) с эталоном в rodata **`0x100054FF`** (байты `00 03 09 05 02`, нулевой — dummy → `3 9 5 2`). На каждую совпавшую ведущую цифру — задержка 50 мс (`FUN_1000239c(0x32)`), выход на первом несовпадении: feedback/timing-оракул. На живом устройстве PIN восстановлен за 23 попытки, теоретический предел 40. Эталон считывает [`attack7/src/extract_pin.py`](../../attack7/src/extract_pin.py), все `10⁴` комбинаций моделирует [`attack7/src/pin_sim.py`](../../attack7/src/pin_sim.py). Подробности — в [`attack7/README.md`](../../attack7/README.md)

## Векторы атаки (отчёты в репозитории)

- `attack1/` — фиксированный ключ шифрования в прошивке (CWE-321): оффлайн-дешифровка из дампа + PoC `decrypt_storage.py`
- `attack2/` — подмена содержимого / evil-maid (CWE-345): известной гаммой шифруется изменённый том. `evil_maid.py` извлекает `your_prize.zip`, проходит 1337 слоёв, внедряет скрипт в исходный `prize.html` и собирает том обратно. Отдельный архив [`your_prize_bounded.zip`](../../attack2/out/your_prize_bounded.zip) сохраняет все слои, а конечная страница ограничена 16 копиями по 16 МиБ; он **не записан в подменённый том**. Бесконечное выделение памяти и крах вкладки экспериментально не проверялись; см. [`attack2/README.md`](../../attack2/README.md)
- `attack3/` — самодельная гамма восстанавливается из холодного дампа по известному открытому тексту FAT12. `B=0x41C64E6D` — множитель из примера POSIX `rand()`, не glibc `rand()`; `W=0x9E3779B1` — константа хеша Кнута. В этом томе **75 значений seed (`0x9E37A9B7`–`0x9E37AA01`)** дают побайтово одинаковую расшифровку 704 КиБ; CRC ZIP не отличает исходное `0x9E37A9EA`. Алгоритм, формула и результаты проверки — в [`attack3/README.md`](../../attack3/README.md)
- `attack4/` — физический тайминг-оракул PIN (CWE-307 и CWE-208): задержка 50 мс на каждую совпавшую ведущую цифру. Текущий [`main.cpp`](../../attack4/pico-encoder-emulator/src/main.cpp) содержит команды `o`, `t<code>` и `n<pin>`; оракул **прогнан на живом сейфе**, PIN `3952` восстановлен за 23 попытки. Полный автоматический перебор `0000–9999` текущим кодом не выполняется. Подключение, физический эксперимент и ограничения — в [`attack4/README.md`](../../attack4/README.md) и [`attack4/WIRING.md`](../../attack4/WIRING.md)
- `attack5/` — модель USB-чтения по сохранённому дампу показывает: после границы LBA 1408 находятся 639 стёртых секторов с 327 168 байтами восстанавливаемой гаммы. LBA 2047 не стёрт. На вход восстановления параметров передаётся смоделированный USB-ответ; шифротекст тома нужен лишь для последующей проверки. Представитель класса seed для этой модели — `0x9E37A9E1`; он даёт точный открытый том, но не обязательно совпадает с представителем из attack3. **USB-ответы живого устройства не снимались**; см. [`attack5/README.md`](../../attack5/README.md)
- `attack6/` — подмена прошивки через BOOTSEL (CWE-494): подготовлены `evil_anypin` (2 изменённых байта инструкции на `0x10000c8c`) и `evil_pin1234` (4 байта эталона PIN). Отличия проверены побайтово; поведение после патча подтверждено rp2040js. BIN/UF2 содержат только префикс программы, а не весь дамп. [`attack6/README.md`](../../attack6/README.md)
- Побочная находка (CWE-613, low, отчёта нет): разблокировка «липкая» — нет auto-lock, таймаута и повторной блокировки, сейф открыт по USB до снятия питания; энкодер после верного PIN не опрашивается (гейт одноразовый — `board_gpio_init` вернул управление в `main`, дальше суперцикл). Перед оформлением подтвердить по Ghidra, что суперцикл энкодер действительно не перечитывает

## Сессия 2 — прочие итоги и поправки

- **`FUN_1000239c` = `sleep_ms(ms)`** (Pico SDK: `make_timeout_time_ms` + WFE/alarm по 64-бит таймеру, GPIO не трогает). Размечено в Ghidra: имя `sleep_ms` на `0x1000239c`, plate-коммент, pre-коммент CWE-208 на call-site `0x10000c92`. Check-in через MCP падает (`unknown consumer`) — правки в открытой сессии, коммит в VCS вручную через GUI
- **boot2 CRC — норма, НЕ аномалия**: сохранённый `0x7A4EB274` = CRC-32/MPEG-2 над первыми `0xFC` байтами (штатный алгоритм Pico SDK); прежнее «расхождение» — от рефлектнутого zlib crc32 (`0xD4A3FD6A`). boot2 не подменён
- **До верного PIN USB неактивен**: `main` зовёт `board_gpio_init()` затем `tud_init(0,0)` (call-site `0x100008a6`); цикл `board_gpio_init` — бесконечный, единственный выход при `{3,9,5,2}`, чистой энкодерной лазейки нет. Атак по USB-протоколу без PIN нет; «без PIN» через USB — только BOOTSEL/PICOBOOT или VBUS-глитч
- **Поправка к SWD-вектору**: запись флага `0x20002ED2=1` НЕ поднимает USB (флаг — только LED-анимация в `app_led_task`); настоящий гейт — возврат из `board_gpio_init`. SWD-разблокировка = форсировать PC мимо цикла
- **V14 (warm-reset флага) — обход реального сброса опровергнут потоком управления**: `main` всегда вызывает проверку PIN перед `tud_init`, а LED-флаг не используется как гейт. Короткое отключение USB могло не сбросить MCU; причина наблюдения на плате требует замера питания и reset. См. [`drafts/NEW_VECTORS.md`](../../drafts/NEW_VECTORS.md)
- **TinyUSB MSC (V3) — эксплуатация не подтверждена**: версия библиотеки из исследованной сборки не установлена. Поиск TinyUSB в [NVD](https://services.nvd.nist.gov/rest/json/cves/2.0?keywordSearch=TinyUSB) на дату проверки не вернул записей, но это не доказывает отсутствие ошибки в данной прошивке
- **rp2040js — эмуляторный стенд** [`attack4/emulator-stand/`](../../attack4/emulator-stand/README.md): запускает настоящий бинарь, вводит PIN по GPIO и различает `3952` и `3951` по флагу. Для срабатывания таймеров стенд вызывает `sim.clock.tick` после `mcu.core.executeInstruction()` и перескакивает ожидание `core.waiting`. Оракул проверен вызовами `sleep_ms(50)`; монтирование USB-MSC стенд не проверяет
- Новые/уточнённые гипотезы — в [`drafts/NEW_VECTORS.md`](../../drafts/NEW_VECTORS.md); статус проверок уточнён в соответствующих отчётах

## Attack4 — эмулятор энкодера (прошивка Pico)

`attack4/pico-encoder-emulator/` — прошивка для второго RP2040 (Raspberry Pi Pico), который выдаёт себя за поворотный энкодер и кнопку сейфа. Текущий код вводит PIN вручную или запускает тайминг-оракул; полный автоматический перебор удалён при переписывании. Управление — командами по USB-serial; сборка — PlatformIO

Текущая распиновка: атакующая Pico `GP4→A` (сейф GPIO29), `GP2→B` (GPIO27), `GP3→SW` (GPIO28), `GP5→GPIO10` (вход SENSE), общая земля. Питание `3V3/VBUS` между платами не соединять; монтаж и границы подтверждения — в [`attack4/WIRING.md`](../../attack4/WIRING.md)

Команды и актуальные настройки принадлежат [`printHelp()` в `main.cpp`](../../attack4/pico-encoder-emulator/src/main.cpp). `SWEEP_SPEED_PCT`, `SWEEP_RADIUS`, `SWEEP_CENTER`, команды `f`/`j`/`g`/`r` были в старой версии контроллера и **отсутствуют сейчас**. Прежний перебор окрестности `3952` не служит описанием текущего PoC

Грабли окружения/сборки:
- Первый `pio run` тянет arduino-pico core рекурсивным клоном (pico-sdk + btstack/tinyusb/mbedtls с тест-данными) — нужно **несколько ГБ** свободного места, иначе падает `No space left on device` на середине клона.
- Порт **переезжает** `/dev/ttyACMx` при каждом переподключении платы — цепляться по стабильному пути `/dev/serial/by-id/usb-Raspberry_Pi_Pico_*` (serial платы `50443405B0780B1C`).
- Баннер печатается **один раз в `setup()`**; arduino-pico при переоткрытии монитора плату не ресетит → при подключении баннера не будет, но команды (`?`,`h`,…) отвечают. Через `pyserial` консоль «молчит», если **не поднять DTR** (`s.dtr=True` при открытии); `pio device monitor`/`screen` поднимают DTR сами.

## Attack4 — оракульный режим (тайминг-атака ≤40 прокруток)

Оракульный режим реализован в [`attack4/pico-encoder-emulator/src/main.cpp`](../../attack4/pico-encoder-emulator/src/main.cpp). В текущей версии **нет** автоматического dumb-sweep; механизм сравнения PIN проверен по декомпиляции и эмулятору настоящего бинаря:

- Проверка PIN на 4-м нажатии (`FUN_10000ab0`, блок с `2 < uVar18`): побайтовое сравнение с эталоном, на **каждую совпавшую ведущую цифру** — `FUN_1000239c(0x32)` = `sleep_ms(50)`. `FUN_1000239c` — обычный `sleep_ms` (busy-wait/WFE по таймеру, **GPIO не трогает**; зовётся ещё с `2` для тика опроса и `200` для кадров анимации). Внутри цикла сравнения ни один GPIO не переключается → все выходы заморожены ровно `50 мс × k`, где `k` — длина совпавшего префикса (0..4). Совпало 4 → `_DAT_d0000014 = 0x400` (SET GPIO10) + `*0x20002ED2 = 1` (unlock); иначе — анимация отказа 3× мигание GPIO10 по 200 мс ≈ 1.2 с, сброс буфера, ввод заново (fail перезапускает ввод в том же блокирующем цикле — подтверждено пользователем на железе)
- Раскладка индикаторных GPIO мишени (таблицы из бинаря по `DAT_10000df0`/`DAT_10000df4`): **GPIO 0–9** — сегменты цифры, таблица цифра→пин `[7,6,5,4,3,2,1,0,9,8]` (горит один); **GPIO 10–13** — позиция/прогресс, таблица `[13,12,11,10]` (GPIO13 на 1-й вводимой цифре … GPIO10 на 4-й); **GPIO 27/28/29** — входы энкодера B/SW/A. **GPIO10 (`0x400`)** несёт всё нужное для оракула: мигает как позиция 4 вокруг момента замера, мигает в анимации отказа, латчится в SET при разблокировке — лучший пин для SENSE
- Подключение SENSE: **Pico GP5 (физический вывод 7) → линия GPIO10 сейфа** (пятак токоограничивающего резистора со стороны чипа, чистые 3.3 В), земля уже общая с энкодерной частью; 3V3/VBUS между платами не соединять
- Замер: перед четвёртым нажатием контроллер ждёт низкого уровня GPIO10, а после нажатия измеряет время до первого перехода в HIGH; `k = round((freeze − base)/step)`. Этот алгоритм использован в опыте, но требует калибровки и правильного подключения SENSE
- Алгоритм атаки (`oracleAttack`): для позиции 0..3 гонять цифру 0..9 с известным префиксом, мерить `k`; верная цифра — единственная с `k ≥ pos+1`, ранний выход при находке (в среднем ~22 ввода, худший 40). В конце ввести найденный PIN и подтвердить unlock по SENSE
- В текущем коде команды `o`, `t<code>`, `n<pin>`, `B<ms>` и `S<ms>` доступны через USB-serial. `Q<ms>` и `D<ms>` пока меняют сохраняемые настройки, но замер `measureThinkTime` их не использует; все команды и значения — в [`printHelp()`](../../attack4/pico-encoder-emulator/src/main.cpp)
- Статус: **ОТРАБОТАНО НА ЖИВОМ СЕЙФЕ (сессия 3)** — оракул восстановил PIN за 23 попытки вслепую. Детали, калибровки и видео — в секции «Attack4 — живое железо (сессия 3)» ниже и в `attack4/README.md`

Пользователь предлагал имя `stupid_50_ms_delay` на самой функции; точнее развести (имя = суть функции `sleep_ms`, «глупость» = комментарий на месте вызова), окончательный выбор — на ПК

Диагностика окружения ноута: атакующая Pico `2e8a:000a` serial `50443405B0780B1C`, `/dev/ttyACM0`, стабильный путь `/dev/serial/by-id/usb-Raspberry_Pi_Pico_50443405B0780B1C-if00`. На ноуте `pyserial` нет — консоль дёргается через `nix-shell -p python3Packages.pyserial` с `dtr=True`. Симптом «плата не видна» был из-за **charge-only/битого кабеля** (`error -71` в журнале ядра, устройство на шине есть, но не энумерируется) — смена кабеля лечит.

## Attack4 — живое железо (сессия 3)

Физический оракул отработан на настоящем сейфе: PIN `3952` восстановлен за **23 попытки** вслепую (предел ≤40). Атакующий контроллер — **RP2040-Zero** (пады подписаны по GP, распиновка кода не менялась: `GP2`→GPIO27 B, `GP3`→GPIO28 SW, `GP4`→GPIO29 A, `GP5`→GPIO10 SENSE, GND). Видео с таймером — `attack4/out/oracle-attack.mp4`.

Тайминг-оракул читается по **GPIO10**: после 4-го нажатия выходы заморожены `50 мс × k`, а физический замер даёт интервалы около `2/52/102/152/202 мс` (k=0..4). Индикатор HIGH после замера не доказывает разблокировку: и отказ, и успешный ввод заканчиваются высоким уровнем. Контроллер классифицирует исход по длительности интервала

Калибровки (в дефолтах `main.cpp`), дались тяжело — каждая закрыла конкретный симптом:

- **резисторы 150–330 Ом последовательно на A (`GP4`) и B (`GP2`)** гасят звон/задвоение фронтов на живых линиях
- **в покое линии в `INPUT_PULLUP`** (не `INPUT`): подтяжка контроллера параллельно слабой внутренней подтяжке сейфа убирает нарастающую со временем наводку («чем дольше подключён — тем сильнее дребезг»)
- детент — **пачка 4 фронтов по 5 мс через `delayMicroseconds`**; `noInterrupts` вокруг пачки вешал USB-CDC — убран, `delayMicroseconds` ждёт до отметки таймера и сам не джиттерит
- **пауза 100 мс между детентами** > 80-мс окна группировки сейфа (`DAT_100010fc`), иначе детенты сливаются/дробятся при авто-наборе
- **4-е нажатие синхронизируется с низкой фазой мигания GPIO10** (это индикатор позиции 4, мигает 300 мс), чтобы фриз читался как низкий интервал

Тайминговые окна декодера энкодера вытащены из образа (`program.bin`, таймер в µs): `DAT_100010f8=30 мс` (приём фронта), `DAT_100010fc=80 мс` (группировка детента), `DAT_100010f0/e08=300 мс` (мигание/тайм-аут). Подтверждены из образа: флаг разблокировки `0x20002ED2`, таблицы сегментов `[7,6,5,4,3,2,1,0,9,8]` и позиций `[13,12,11,10]`, эталон PIN по `DAT_10000e10=0x100054ff`.

После короткого отключения USB наблюдали, что сейф остаётся открытым; для чистого повтора его полностью обесточивали на 5–10 с. Настоящий сброс перезапускает `main` и повторяет проверку PIN, поэтому LED-флаг не объясняет обход. Был ли при коротком отключении сброс MCU, не измеряли; возможно, это тот же липкий сеанс без перезапуска

Прошивка/окружение: `pio run -t upload` на этом ноуте (NixOS) ненадёжен — авто-детект хватает `/dev/ttyS0`, а его picotool-поток ждёт авто-монтирование RPI-RP2, которого на NixOS нет (+ `pio` в bwrap). Надёжная заливка — **`picotool load -x <uf2>`** после 1200-touch (`pyserial dtr=False`) или ручного BOOTSEL; `platformio.ini` прибит `upload_port = /dev/ttyACM*` (фикс ttyS0). udev-варнинг `pio` — ложный (правила из `~/huix/nixos/services/utils/embedded.nix` активны, доступ есть; ругается bwrap-обёртка). `-f` у picotool не работает — прошивка не выставляет reset-интерфейс.

## Сессия 4 — доразбор пинов, SWD и V14

- **GPIO16 (WS2812) — возможный дополнительный сигнал**: код `FUN_10001218` отправляет различимые цвета набора `(0,0,0x20)`, успеха `(0,0x20,0)` и отказа `(0x20,0,0)` после цикла с `sleep_ms(50)`. Тайминг по GPIO16 следует из порядка вызовов, но аппаратно не снимался; GPIO10 проверен на живом сейфе. См. [`attack4/README.md`](../../attack4/README.md)
- **SWD**: аппаратного fuse/RDP у RP2040 нет, а в исследованном прикладном коде не обнаружена защита порта; физический доступ к SWCLK/SWDIO на этой плате ещё не проверен. Уточнения — в V8 [`drafts/NEW_VECTORS.md`](../../drafts/NEW_VECTORS.md)
- **V14 опровергнут как обход настоящего reset**: `main` всегда вызывает `board_gpio_init` до `tud_init` и не читает флаг `0x20002ED2` как гейт. Краткое отключение USB могло не перезагрузить MCU, что согласуется с липкой разблокировкой (CWE-613); причинность требует замера питания
- **Fault-injection (V9/V27) — уточнение**: рантайм-глитч по `bne 0x10000c8c` даёт эффект `evil_anypin`, но образ не меняет → хэш-детект из attack6 его не ловит. Дописано в V27
